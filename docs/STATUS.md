# EH3D-PHOENIX-PCB: status

## Current state

EH3D-PHOENIX-PCB is early code. Beside the base that every repository of the suite carries, it has a Rust workspace with a library and two commands, `phoenix inventory` and `phoenix eagle-rate` (the second measures how many EAGLE files the reader reads, on copies, in redacted form); the first counts the design files of a private folder in redacted mode (counts by extension, kind and declared version, and one fingerprint). It has run only on folders made by its own tests, never on real design files. It also has the foundations of the design model in the crate `eh3d-phoenix-model`: lengths in integer nanometres and angles in integer micro-degrees with a checked range, orientation predicates in 64-bit integers, arcs as end points plus a sweep, UUID v7 object ids from a generator with an injected clock and random source, and canonical JSON (RFC 8785) with quantised millimetre and degree values. The `.phoenixproj` project file (crate `eh3d-phoenix-project`) and the board model with reversible operations (crate `eh3d-phoenix-board`) also exist, tried on generated data only. The board crate also computes the connectivity of each net and checks sizes and clearances against a rule file, and the crate `eh3d-phoenix-eagle` reads EAGLE XML libraries, boards and schematics into a summary and writes the XML tree back identically; its first measurement over copies of a private corpus reads 734 of 2263 files (most of the rest start like the binary files of the old versions; see PPCB-004); a small crate (`eh3d-phoenix-hub`) is the common interface of the importers, with the EAGLE reader behind it; a crate (`eh3d-phoenix-export`) writes the Gerber X2, Excellon and `.eh3dproj` 1.0.0 files of a board through EH3D-CORE-LIBS and EH3D-COMMON; all of it is tried on generated or hand-made data only. `docs/GATE_F1.md` says what the first gate checks and what it does not. A crate (`eh3d-phoenix-schematic`) holds the schematic model and checks it against a board. The board model also holds silkscreen text and strokes, which the rule check judges against the pads and the export writes as a Gerber legend file; the schematic crate can hold a drawing (sheets, placed parts, wires) that is compared with the net list and with the board; the crate `eh3d-phoenix-eagle-board` writes a board as an EAGLE XML file and reads it back, compared by a signature without ids on 60 generated variants of one board, and the contract for pairs of EAGLE binary files and their XML is written in `eh3d-phoenix-eagle` (`pairs`). No file written here has been opened in EAGLE, there is no reader of the binary files (it waits for pairs of files from the owner), there is no schematic editor, no import of foreign designs other than the board file written by this code, no editor, and the rules cover only part of the checks planned. The crate `eh3d-phoenix-rules` holds the rule engine and the connectivity: it reads the limits from a rule file (JSON) or from the design rules of an EAGLE board, checks a board in a fixed order with the measured value and the limit of each finding, derives the nets from the geometry with a joining tolerance, finds shorts and unrouted nets, compares the nets of a board with those of a schematic and keeps confirmed and inconclusive findings in two lists; the commands `phoenix check` and `phoenix connectivity` print the report as text in eight languages or as JSON. It has been tried on boards made by hand only and has never been compared with the reference tool, so PPCB-007 and PPCB-008 stay at prototype. A crate (`eh3d-phoenix-stackup`) computes the impedance, effective permittivity, conductor and dielectric loss, delay and track width of microstrip, stripline, coplanar and coupled lines from published quasi-static formulas, each with its range and a warning outside it (command `phoenix stackup`, see `docs/STACKUP.md`); it is a prototype that has never been compared with a field solver or with the measurement of a board. A crate (`eh3d-phoenix-rf`) holds the RF tools of everyday use (command `phoenix rf`, see `docs/RF.md`): a reader and writer of Touchstone files, the S, Z, Y and ABCD parameters of two-ports with their conversions, the cascade and the figures read from them (VSWR, return and insertion loss, group delay, gain, stability, passivity, reciprocity), L networks, single stubs and quarter-wave sections for complex impedances, the coordinates of the Smith chart and Butterworth, Chebyshev and Bessel ladder filters of ideal components; it is a prototype tested with values of textbooks and with properties, and it has never been compared with a network analyser, a field solver or another RF program. A crate (`eh3d-phoenix-viewer`) is a read-only viewer prototype of boards and schematics (command `phoenix view`, see `docs/VIEWER.md`): the drawing primitives, the layers with their colours, the view, the selection by position with a spatial index, the highlight of a net and the measure are tested without a screen, `phoenix view --bench` times the preparation of the data on three synthetic boards, and a window of egui behind the `gui` feature draws it; the window has never been seen on a screen and the drawing on a screen was not measured. A crate (`eh3d-phoenix-kicad`) reads the files of KiCad 6 to 9 into the model that the EAGLE files go into (command `phoenix kicad-read`, see `docs/KICAD.md`): symbol libraries, footprints, schematics with their sheets and the nets computed from the drawing, boards in integer nanometres and the project file, behind the format hub with a quality report and a fidelity level; it is a prototype written from the public description of the formats and tried on files written by hand for the tests, and it has never been compared with KiCad or run on a public collection of designs. A crate (`eh3d-phoenix-sanitizer`) is the analysis half of the library sanitizer (command `phoenix sanitize`, see `docs/SANITIZER.md`): it takes the inventory of a folder of EAGLE libraries with the reader and the limits of the corpus crate (a damaged file is noted and the walk goes on), hashes footprints and symbols canonically, scores near duplicates against a threshold, forms groups for the owner to confirm, names the item to keep in each group and writes an HTML report, the same report as JSON and a plan of the master library; it never rewrites a library and never applies the plan, and it is a prototype tried only on libraries made by its own tests, never on real libraries. A crate (`eh3d-phoenix-erc`) is the electrical rule check of a schematic (command `phoenix erc`, see `docs/ERC.md`): pins on no net, nets with a single pin, pin types that a matrix in `config/erc.cfg` does not allow together, inputs with no driver, power inputs with no source, net names that look alike, references used twice, empty values, parts without a footprint and loose wires, with confirmed and inconclusive findings in two lists in a fixed order; the pin types are held by the schematic and read from the `direction` of EAGLE pins. A crate (`eh3d-phoenix-sync`) compares a schematic and a board by the identity of their parts (command `phoenix sync`) and makes the changes of the transfer to the board, or of the annotation back into the schematic, as a package that is planned as a dry run, applied as one step of an undo/redo history, undone and redone exactly and applied twice with no effect; and the rule file of the second format (`phoenix-rules/2`) holds net classes whose track width and via limits `phoenix check` verifies. All of it is a prototype tried on schematics and boards made by hand and by the tests, never compared with the reference tool; there is still no schematic editor. A crate (`eh3d-phoenix-sim`) simulates circuits with a solver of our own (command `phoenix sim`, see `docs/SIM.md` and `docs/adr/0010-own-circuit-simulator.md`): a reader and a writer of SPICE-style netlists, the netlist of a schematic with a report of what could not be translated, linear circuits and circuits with diodes by modified nodal analysis, the DC operating point (Newton-Raphson with source stepping as a fallback), AC sweeps with magnitude, phase and group delay, transient analysis (backward Euler and trapezoidal, fixed and adaptive step), CSV and JSON tables, and a check of its AC response against the ladder filters of the RF crate; it is a prototype tested with textbook values and properties, never compared with SPICE or with a measurement, and it has no transistors.

## Capabilities

The official state of each capability is in REQUIREMENTS.md: 30 requirements: 15 `prototype` (PPCB-001, PPCB-002, PPCB-003, PPCB-007, PPCB-008, PPCB-009, PPCB-011, PPCB-012, PPCB-014, PPCB-017, PPCB-021, PPCB-022, PPCB-024, PPCB-029, PPCB-030) and 15 `planned`. This page never states a state that REQUIREMENTS.md does not.

## Open questions

* Which user-interface and rendering stack to use: candidates are egui on wgpu with a custom canvas, iced, Slint, or everything on wgpu. It is decided after a short prototype measured on small, medium and large boards. The prototype exists (egui on eframe with a canvas of our own, `docs/adr/0009-first-interface-stack.md`) and its choice stays provisional until the drawing is measured on a real screen; only the preparation of the data has been timed.
* Which 2D geometry library to use for offsets and boolean operations, decided with a benchmark on degenerate input.
* Whether the first golden files can be produced semi-automatically from the command line of the reference tool.
* Whether the simulator of our own (`docs/adr/0010-own-circuit-simulator.md`, provisional) stays the engine of the circuit simulation, and which existing engine to compare it with, once its licence and platform support are checked.

## Needs from other repositories

* EH3D-COMMON: the project container (`eh3d-container`) and the diagnostic crate (`eh3d-diagnostic`), already used; this repository builds next to it
* EH3D-CORE-LIBS: geometry, readers and the Gerber and Excellon writers
* EH3D-VALIDATION-LAB: the corpus and the golden-file oracle

## Known technical debt and omitted tests

* 952 tests of the Rust code and 3 of the base; the inventory tests build their own folders and never touch a real project.
* The window of the viewer has never been seen on a screen, a graphics card or an operating system: the lints of CI check that it builds, nothing more. The timing of `phoenix view --bench` covers the preparation of the primitives and the selection by position, not the drawing, and its numbers depend on the computer.
* The manufacturing export (`docs/EXPORT.md`) has been read back only by the parsers of EH3D-CORE-LIBS: no independent Gerber or Excellon viewer, no manufacturer and no assembler has opened a file of it, the rule for the rotation of a bottom part and the columns of the `jlc-like` profile are settings that nobody has compared with a real sample, and copper pours, blind vias and polygon pads are not written.
* The model foundations are checked with generated and edge cases only: there is no design object on top of them yet, so the identities across save, migration and reopening are untested. Duplicate keys in an input JSON text are not detected before canonical writing. The system random source for ids is not cryptographic (ids need uniqueness, not secrecy).
* Not tested: a corpus of hundreds of thousands of files, folders synchronised by a cloud service, and links (they are skipped and counted; the test for it runs only on Unix-like systems).
* The kind of a file is read from its first bytes only: a file that starts like XML but is damaged later is counted by its start.
* `cargo deny` is not run in the CI yet: it needs a third-party action that the repository settings do not allow; `deny.toml` exists and has not been run on a computer.
