# EH3D-PHOENIX-PCB: status

## Current state

EH3D-PHOENIX-PCB is early code. Beside the base that every repository of the suite carries, it has a Rust workspace with a library and two commands, `phoenix inventory` and `phoenix eagle-rate` (the second measures how many EAGLE files the reader reads, on copies, in redacted form); the first counts the design files of a private folder in redacted mode (counts by extension, kind and declared version, and one fingerprint). It has run only on folders made by its own tests, never on real design files. It also has the foundations of the design model in the crate `eh3d-phoenix-model`: lengths in integer nanometres and angles in integer micro-degrees with a checked range, orientation predicates in 64-bit integers, arcs as end points plus a sweep, UUID v7 object ids from a generator with an injected clock and random source, and canonical JSON (RFC 8785) with quantised millimetre and degree values. The `.phoenixproj` project file (crate `eh3d-phoenix-project`) and the board model with reversible operations (crate `eh3d-phoenix-board`) also exist, tried on generated data only. The board crate also computes the connectivity of each net and checks sizes and clearances against a rule file, and the crate `eh3d-phoenix-eagle` reads EAGLE XML libraries, boards and schematics into a summary and writes the XML tree back identically; its first measurement over copies of a private corpus reads 734 of 2263 files (most of the rest start like the binary files of the old versions; see PPCB-004); a small crate (`eh3d-phoenix-hub`) is the common interface of the importers, with the EAGLE reader behind it; a crate (`eh3d-phoenix-export`) writes the Gerber X2, Excellon and `.eh3dproj` 1.0.0 files of a board through EH3D-CORE-LIBS and EH3D-COMMON; all of it is tried on generated or hand-made data only. `docs/GATE_F1.md` says what the first gate checks and what it does not. A crate (`eh3d-phoenix-schematic`) holds the schematic model and checks it against a board. The board model also holds silkscreen text and strokes, which the rule check judges against the pads and the export writes as a Gerber legend file; the schematic crate can hold a drawing (sheets, placed parts, wires) that is compared with the net list and with the board; the crate `eh3d-phoenix-eagle-board` writes a board as an EAGLE XML file and reads it back, compared by a signature without ids on 60 generated variants of one board, and the contract for pairs of EAGLE binary files and their XML is written in `eh3d-phoenix-eagle` (`pairs`). No file written here has been opened in EAGLE, there is no reader of the binary files (it waits for pairs of files from the owner), there is no import of foreign designs other than the board file written by this code, no editor, and the rules cover only part of the checks planned. The crate `eh3d-phoenix-rules` holds the rule engine and the connectivity: it reads the limits from a rule file (JSON) or from the design rules of an EAGLE board, checks a board in a fixed order with the measured value and the limit of each finding, derives the nets from the geometry with a joining tolerance, finds shorts and unrouted nets, compares the nets of a board with those of a schematic and keeps confirmed and inconclusive findings in two lists; the commands `phoenix check` and `phoenix connectivity` print the report as text in eight languages or as JSON. It has been tried on boards made by hand only and has never been compared with the reference tool, so PPCB-007 and PPCB-008 stay at prototype. A crate (`eh3d-phoenix-stackup`) computes the impedance, effective permittivity, conductor and dielectric loss, delay and track width of microstrip, stripline, coplanar and coupled lines from published quasi-static formulas, each with its range and a warning outside it (command `phoenix stackup`, see `docs/STACKUP.md`); it is a prototype that has never been compared with a field solver or with the measurement of a board. A crate (`eh3d-phoenix-rf`) holds the RF tools of everyday use (command `phoenix rf`, see `docs/RF.md`): a reader and writer of Touchstone files, the S, Z, Y and ABCD parameters of two-ports with their conversions, the cascade and the figures read from them (VSWR, return and insertion loss, group delay, gain, stability, passivity, reciprocity), L networks, single stubs and quarter-wave sections for complex impedances, the coordinates of the Smith chart and Butterworth, Chebyshev and Bessel ladder filters of ideal components; it is a prototype tested with values of textbooks and with properties, and it has never been compared with a network analyser, a field solver or another RF program. A crate (`eh3d-phoenix-viewer`) is a viewer and editor prototype of boards and schematics (command `phoenix view`, see `docs/VIEWER.md`): the drawing primitives, the layers with their colours, the view, the selection by position with a spatial index, the highlight of a net and the measure are tested without a screen, and so is the state of editing (tools, drags, keys, undo and redo, the findings of the rules that each edit adds and resolves, the ratsnest, the electrical check of a schematic, the dry run of the transfer to the board and of the annotation back, and saving under another name with a copy of the file replaced); `phoenix view --bench` times the preparation of the data on three synthetic boards, and a window of egui behind the `gui` feature draws and drives all of it; the window has never been seen on a screen or used with a mouse, and the drawing on a screen and the time of an edit on a large board were not measured. A crate (`eh3d-phoenix-kicad`) reads the files of KiCad 6 to 9 into the model that the EAGLE files go into (command `phoenix kicad-read`, see `docs/KICAD.md`): symbol libraries, footprints, schematics with their sheets and the nets computed from the drawing, boards in integer nanometres and the project file, behind the format hub with a quality report and a fidelity level; it is a prototype written from the public description of the formats and tried on files written by hand for the tests, and it has never been compared with KiCad or run on a public collection of designs. A crate (`eh3d-phoenix-sanitizer`) is the analysis half of the library sanitizer (command `phoenix sanitize`, see `docs/SANITIZER.md`): it takes the inventory of a folder of EAGLE libraries with the reader and the limits of the corpus crate (a damaged file is noted and the walk goes on), hashes footprints and symbols canonically, scores near duplicates against a threshold, forms groups for the owner to confirm, names the item to keep in each group and writes an HTML report, the same report as JSON and a plan of the master library; it never rewrites a library and never applies the plan, and it is a prototype tried only on libraries made by its own tests, never on real libraries. A crate (`eh3d-phoenix-erc`) is the electrical rule check of a schematic (command `phoenix erc`, see `docs/ERC.md`): pins on no net, nets with a single pin, pin types that a matrix in `config/erc.cfg` does not allow together, inputs with no driver, power inputs with no source, net names that look alike, references used twice, empty values, parts without a footprint and loose wires, with confirmed and inconclusive findings in two lists in a fixed order; the pin types are held by the schematic and read from the `direction` of EAGLE pins. A crate (`eh3d-phoenix-sync`) compares a schematic and a board by the identity of their parts (command `phoenix sync`) and makes the changes of the transfer to the board, or of the annotation back into the schematic, as a package that is planned as a dry run, applied as one step of an undo/redo history, undone and redone exactly and applied twice with no effect; and the rule file of the second format (`phoenix-rules/2`) holds net classes whose track width and via limits `phoenix check` verifies. All of it is a prototype tried on schematics and boards made by hand and by the tests, never compared with the reference tool. The schematic editor (`docs/SCHEMATIC_EDIT.md`) is a prototype too, tried on schematics made by the tests only: reversible operations (place, move, turn, mirror, delete, copy and paste, values and references, wires, net labels, power ports and bus labels) in the module `edit` of the schematic crate, with the nets made again from the drawing; its state without a screen in the crate `eh3d-phoenix-schedit` (grid and snapping, selection, wires that follow the pins, a palette of symbols, the electrical check after each change, the transfer to the board with a preview and the net list for the simulator); the command `phoenix schedit`; and an editing mode of the window that has never been seen on a screen. A crate (`eh3d-phoenix-sim`) simulates circuits with a solver of our own (command `phoenix sim`, see `docs/SIM.md` and `docs/adr/0010-own-circuit-simulator.md`): a reader and a writer of SPICE-style netlists, the netlist of a schematic with a report of what could not be translated, linear circuits, diodes (series resistance, junction capacitance, breakdown), bipolar and MOS transistors, voltage-controlled switches and op-amp macromodels by modified nodal analysis (`docs/SIM_NONLINEAR.md`), the DC operating point (Newton-Raphson with gmin stepping and source stepping as fallbacks and a report of its iterations and residual), the DC sweep of a source, AC sweeps with magnitude, phase and group delay, the noise at an output, transient analysis (backward Euler and trapezoidal, fixed step and an adaptive step that stops at the corners of the sources), CSV and JSON tables, and a check of its AC response against the ladder filters of the RF crate; it is a prototype tested with textbook values, closed-form solutions and properties, never compared with SPICE or with a measurement, and its device models are simple. A crate (`eh3d-phoenix-route`) holds the editing and routing logic that needs no window (commands `phoenix route` and `phoenix ratsnest`, see `docs/ROUTE.md`): the ratsnest of the connections still to be routed, a router for pieces at 0, 45 and 90 degrees that takes the width and the vias from the rules and the net class and stops in front of obstacles or goes around them, reversible editing operations with undo and redo, and the live check that reports what an edit adds and removes; a prototype tried on boards made by hand and by the tests, with no arcs, no copper zones and no push and shove. The same crate exchanges files with an external autorouter (command `phoenix autoroute`, see `docs/AUTOROUTE.md`): the board as a Specctra DSN file, a Specctra session read as a plan whose routes are checked against the rules and applied all or nothing, and an adapter that starts a program, off unless a settings file and a command line option both say so; a prototype tried with sessions made by hand, never with a real autorouter. A crate (`eh3d-phoenix-zones`) fills copper zones (command `phoenix zones`, see `docs/ZONES.md`): the outline cut into convex pieces, the copper of other nets, the edge of the board and the zones of a higher priority taken out with exact integer polygon clipping by the clearance of the rules, thermal reliefs on the pads of the net, islands judged by area, width and connection, and a check that measures a fill against the board; a prototype tried on boards made by hand and by the tests, with the fill kept as convex polygons that is not yet written in the Gerber files. A crate (`eh3d-phoenix-lengths`) gives the copper length and the delay of each net, with the delay of each layer taken from the stack-up, judges groups of nets that must match in length and differential pairs by their length difference, width, separation and uncoupled length (command `phoenix lengths`, see `docs/LENGTHS.md`); a prototype tried on boards made by hand and by the tests, whose length is the total copper of a net and which tunes nothing. A crate (`eh3d-phoenix-script`) holds the script interpreter (commands `phoenix script run`, `phoenix script report` and `phoenix cam-import`, see `docs/SCRIPT.md`): a reader of script files of the command language of the previous workflow, a run of `GRID`, `LAYER`, `DISPLAY`, `CHANGE`, `WIRE`, `VIA`, `CIRCLE`, `RECT`, `TEXT`, `MOVE`, `ROTATE`, `DELETE`, `NAME`, `VALUE`, `SET`, `GROUP`, `RATSNEST`, `DRC`, `ERC`, `WRITE`, `OPEN` and `SCRIPT` as reversible operations of the board, all or nothing and with an undo that gives the original back byte for byte, a compatibility report that lists every command of every script as equivalent, adapted or pending with its cause (text, JSON and HTML) and a reader of output jobs into an export profile; it is a prototype built from the public description of the language and tested with scripts written for it, never compared with the original tool and never run on the author's own scripts. A crate (`eh3d-phoenix-rfgen`) draws microstrip RF structures from the stack-up and the frequency (command `phoenix rfgen`, see `docs/RFGEN.md`): lines, mitered bends, curves and tapers, open and short-circuited stubs, the single-stub, quarter-wave and L matches built on the RF tools, stepped-impedance low-pass and coupled-line band-pass filters, a Wilkinson divider, a branch-line coupler, patch and dipole antennas and an edge SMA launch with a via fence; each result is one all-or-nothing batch of reversible operations of the board (the board crate gained operations to add and remove copper zones and footprints for it) with a report of the dimensions, the formulas used with their sources and ranges, the warnings and the rule check of the result, which is refused when it adds an error. It is a prototype tested with values of textbooks and with properties on boards made by the tests, and it has never been compared with an electromagnetic simulator or with a measurement; discontinuities and dispersion are not modelled, and the isolation resistor and the land pattern of the connector are generic. A crate (`eh3d-phoenix-libedit`) is the library editor (commands `phoenix libedit` and `phoenix footprint`, a library mode of the window, see `docs/LIBRARY_EDIT.md`): an EAGLE library in memory with reversible all-or-nothing operations on footprints, symbols and devices (pads, lines, arcs, texts, pins, openings of the mask and the paste, gates, variants and the connection of pins to pads) with undo and redo, checks with the codes `PHOENIX-LIB-001` to `014`, saving as a new file that is read back and compared with a copy of the original beside it, generators of footprints by the method of IPC-7351B whose values in `config/footprints.cfg` were entered by hand and are not checked against a datasheet, and the replacement of an item by the master candidate of the sanitizer only after the confirmation of each step; it is a prototype tried only on libraries made by its tests, no EAGLE has opened a file it wrote and its window has never been seen on a screen. A crate (`eh3d-phoenix-oracle`) holds reference cases for the calculations (command `phoenix oracle`, see `docs/ORACLE.md`): 73 cases in `tests/oracle/`, 58 of them cited with a published value or a closed-form solution, its source and its tolerance and run against the real functions of the stack-up, RF, simulator, rules, lengths and zone crates, and 15 pending with the reason and no number; passing them shows that a calculation reproduces a published formula or a closed-form solution, it does not compare anything with EAGLE, KiCad, a field solver, a SPICE program or a measurement (the plan to do so is written and has not been run), and it changes no state of this repository.

## Capabilities

The official state of each capability is in REQUIREMENTS.md: 30 requirements: 18 `prototype` (PPCB-001, PPCB-002, PPCB-003, PPCB-007, PPCB-008, PPCB-009, PPCB-011, PPCB-012, PPCB-014, PPCB-015, PPCB-016, PPCB-017, PPCB-019, PPCB-021, PPCB-022, PPCB-024, PPCB-029, PPCB-030) and 12 `planned`. This page never states a state that REQUIREMENTS.md does not.

## Open questions

* Which user-interface and rendering stack to use: candidates are egui on wgpu with a custom canvas, iced, Slint, or everything on wgpu. It is decided after a short prototype measured on small, medium and large boards. The prototype exists (egui on eframe with a canvas of our own, `docs/adr/0009-first-interface-stack.md`) and its choice stays provisional until the drawing is measured on a real screen; only the preparation of the data has been timed.
* Which 2D geometry library to use for offsets and boolean operations, decided with a benchmark on degenerate input.
* Whether the first golden files can be produced semi-automatically from the command line of the reference tool.
* Whether the simulator of our own (`docs/adr/0010-own-circuit-simulator.md`, provisional) stays the engine of the circuit simulation, and which existing engine to compare it with, once its licence and platform support are checked.

## Needs from other repositories

* EH3D-COMMON: the project container (`eh3d-container`), the diagnostic crate (`eh3d-diagnostic`) and the materials database (`eh3d-materials`, used by the stack-up calculation and by `phoenix materials`), already used; this repository builds next to it
* EH3D-CORE-LIBS: geometry, readers and the Gerber and Excellon writers
* EH3D-VALIDATION-LAB: the corpus and the golden-file oracle

## Known technical debt and omitted tests

* 2015 tests of the Rust code and 3 of the base; the inventory tests build their own folders and never touch a real project.
* The reference cases (`docs/ORACLE.md`) compare the calculations only with published formulas and closed-form solutions: the 15 pending cases and the whole plan of comparison with EAGLE, KiCad, a field solver and a SPICE program have not been run, and some tolerances are chosen in the case files and say so.
* The window of the viewer has never been seen on a screen, a graphics card or an operating system: the lints of CI check that it builds, nothing more. The timing of `phoenix view --bench` covers the preparation of the primitives and the selection by position, not the drawing, and its numbers depend on the computer.
* The manufacturing export (`docs/EXPORT.md`) has been read back only by the parsers of EH3D-CORE-LIBS and by the import of this repository (`docs/GERBER_IMPORT.md`): no independent Gerber or Excellon viewer, no manufacturer and no assembler has opened a file of it, the rule for the rotation of a bottom part and the columns of the `jlc-like` profile are settings that nobody has compared with a real sample, and copper pours, blind vias and polygon pads are not written.
* The import of Gerber and Excellon files (`docs/GERBER_IMPORT.md`) and the panelization (`docs/PANEL.md`) have been tried on files and boards made by the tests only: the import has never read a file written by a CAD program or a manufacturer and its geometry has never been compared with a reference viewer, and no manufacturer has accepted a panel.
* The bill of materials with costs (`docs/BOM.md`) and the 3D assembly (`docs/ASSEMBLY3D.md`) have been tried on boards and files made by the tests only: the tariffs of `config/costs.cfg` are an example and not the quote of any maker, the prices are the ones of a file the user gives and are never checked, no STEP file from a component maker has been read, a component is only its enclosing box, no CAD program has opened the OBJ and STEP files it writes, and the window that would draw the scene is not written.
* The model foundations are checked with generated and edge cases only: there is no design object on top of them yet, so the identities across save, migration and reopening are untested. Duplicate keys in an input JSON text are not detected before canonical writing. The system random source for ids is not cryptographic (ids need uniqueness, not secrecy).
* Not tested: a corpus of hundreds of thousands of files, folders synchronised by a cloud service, and links (they are skipped and counted; the test for it runs only on Unix-like systems).
* The kind of a file is read from its first bytes only: a file that starts like XML but is damaged later is counted by its start.
* `cargo deny` is not run in the CI yet: it needs a third-party action that the repository settings do not allow; `deny.toml` exists and has not been run on a computer.
