# EH3D-PHOENIX-PCB: status

## Current state

EH3D-PHOENIX-PCB is early code. Beside the base that every repository of the suite carries, it has a Rust workspace with a library and two commands, `phoenix inventory` and `phoenix eagle-rate` (the second measures how many EAGLE files the reader reads, on copies, in redacted form); the first counts the design files of a private folder in redacted mode (counts by extension, kind and declared version, and one fingerprint). It has run only on folders made by its own tests, never on real design files. It also has the foundations of the design model in the crate `eh3d-phoenix-model`: lengths in integer nanometres and angles in integer micro-degrees with a checked range, orientation predicates in 64-bit integers, arcs as end points plus a sweep, UUID v7 object ids from a generator with an injected clock and random source, and canonical JSON (RFC 8785) with quantised millimetre and degree values. The `.phoenixproj` project file (crate `eh3d-phoenix-project`) and the board model with reversible operations (crate `eh3d-phoenix-board`) also exist, tried on generated data only. The board crate also computes the connectivity of each net and checks sizes and clearances against a rule file, and the crate `eh3d-phoenix-eagle` reads EAGLE XML libraries, boards and schematics into a summary and writes the XML tree back identically; its first measurement over copies of a private corpus reads 734 of 2263 files (most of the rest start like the binary files of the old versions; see PPCB-004); a small crate (`eh3d-phoenix-hub`) is the common interface of the importers, with the EAGLE reader behind it; a crate (`eh3d-phoenix-export`) writes the Gerber X2, Excellon and `.eh3dproj` 1.0.0 files of a board through EH3D-CORE-LIBS and EH3D-COMMON; all of it is tried on generated or hand-made data only. `docs/GATE_F1.md` says what the first gate checks and what it does not. A crate (`eh3d-phoenix-schematic`) holds the schematic model and checks it against a board. The board model also holds silkscreen text and strokes, which the rule check judges against the pads and the export writes as a Gerber legend file; the schematic crate can hold a drawing (sheets, placed parts, wires) that is compared with the net list and with the board; the crate `eh3d-phoenix-eagle-board` writes a board as an EAGLE XML file and reads it back, compared by a signature without ids on 60 generated variants of one board, and the contract for pairs of EAGLE binary files and their XML is written in `eh3d-phoenix-eagle` (`pairs`). No file written here has been opened in EAGLE, there is no reader of the binary files (it waits for pairs of files from the owner), there is no import of foreign designs other than the board file written by this code, no editor, and the rules cover only part of the checks planned. The crate `eh3d-phoenix-rules` holds the rule engine and the connectivity: it reads the limits from a rule file (JSON) or from the design rules of an EAGLE board, checks a board in a fixed order with the measured value and the limit of each finding, derives the nets from the geometry with a joining tolerance, finds shorts and unrouted nets, compares the nets of a board with those of a schematic and keeps confirmed and inconclusive findings in two lists; the commands `phoenix check` and `phoenix connectivity` print the report as text in eight languages or as JSON. It has been tried on boards made by hand only and has never been compared with the reference tool, so PPCB-007 and PPCB-008 stay at prototype. The advanced design rule checks (`phoenix check --advanced`, `docs/DRC_ADVANCED.md`) belong to PPCB-008 and are a prototype too, tried on boards made by hand only; the figures of their spacing table are not verified against the standard. A crate (`eh3d-phoenix-stackup`) computes the impedance, effective permittivity, conductor and dielectric loss, delay and track width of microstrip, stripline, coplanar and coupled lines from published quasi-static formulas, each with its range and a warning outside it (command `phoenix stackup`, see `docs/STACKUP.md`); it is a prototype that has never been compared with a field solver or with the measurement of a board. A crate (`eh3d-phoenix-rf`) holds the RF tools of everyday use (command `phoenix rf`, see `docs/RF.md`): a reader and writer of Touchstone files, the S, Z, Y and ABCD parameters of two-ports with their conversions, the cascade and the figures read from them (VSWR, return and insertion loss, group delay, gain, stability, passivity, reciprocity), L networks, single stubs and quarter-wave sections for complex impedances, the coordinates of the Smith chart and Butterworth, Chebyshev and Bessel ladder filters of ideal components; it is a prototype tested with values of textbooks and with properties, and it has never been compared with a network analyser, a field solver or another RF program. A crate (`eh3d-phoenix-viewer`) is a viewer and editor prototype of boards and schematics (command `phoenix view`, see `docs/VIEWER.md`): the drawing primitives, the layers with their colours, the view, the selection by position with a spatial index, the highlight of a net and the measure are tested without a screen, and so is the state of editing (tools, drags, keys, undo and redo, the findings of the rules that each edit adds and resolves, the ratsnest, the electrical check of a schematic, the dry run of the transfer to the board and of the annotation back, and saving under another name with a copy of the file replaced); `phoenix view --bench` times the preparation of the data on three synthetic boards, and a window of egui behind the `gui` feature draws and drives all of it; the window has never been seen on a screen or used with a mouse, and the drawing on a screen and the time of an edit on a large board were not measured. A crate (`eh3d-phoenix-kicad`) reads the files of KiCad 6 to 9 into the model that the EAGLE files go into (command `phoenix kicad-read`, see `docs/KICAD.md`): symbol libraries, footprints, schematics with their sheets and the nets computed from the drawing, boards in integer nanometres and the project file, behind the format hub with a quality report and a fidelity level; it is a prototype written from the public description of the formats and tried on files written by hand for the tests, and it has never been compared with KiCad or run on a public collection of designs. The same crate writes a board, a schematic with its sheets, the footprints of a board and the symbols of a schematic as KiCad 8 files (command `phoenix kicad-export`, see `docs/KICAD_EXPORT.md`), with a report of what the model cannot say; its files are read back by the readers of the crate and have never been opened in KiCad. A crate (`eh3d-phoenix-ipclib`) is an own library of footprints by the method of IPC-7351B (the command `phoenix ipc`, see `docs/IPC_LIBRARY.md`) and the bulk import of EAGLE and KiCad libraries into an index with a quality report (the command `phoenix libindex`, see `docs/LIBINDEX.md`); the dimensions of its families were written by hand and are not checked against a datasheet, no EAGLE or KiCad has opened a file it wrote, and it has only been tried on libraries made by its tests. A crate (`eh3d-phoenix-sanitizer`) is the analysis half of the library sanitizer (command `phoenix sanitize`, see `docs/SANITIZER.md`): it takes the inventory of a folder of EAGLE libraries with the reader and the limits of the corpus crate (a damaged file is noted and the walk goes on), hashes footprints and symbols canonically, scores near duplicates against a threshold, forms groups for the owner to confirm, names the item to keep in each group and writes an HTML report, the same report as JSON and a plan of the master library; it never rewrites a library and never applies the plan, and it is a prototype tried only on libraries made by its own tests, never on real libraries. A crate (`eh3d-phoenix-erc`) is the electrical rule check of a schematic (command `phoenix erc`, see `docs/ERC.md`): pins on no net, nets with a single pin, pin types that a matrix in `config/erc.cfg` does not allow together, inputs with no driver, power inputs with no source, net names that look alike, references used twice, empty values, parts without a footprint and loose wires, with confirmed and inconclusive findings in two lists in a fixed order; the pin types are held by the schematic and read from the `direction` of EAGLE pins. A crate (`eh3d-phoenix-sync`) compares a schematic and a board by the identity of their parts (command `phoenix sync`) and makes the changes of the transfer to the board, or of the annotation back into the schematic, as a package that is planned as a dry run, applied as one step of an undo/redo history, undone and redone exactly and applied twice with no effect; and the rule file of the second format (`phoenix-rules/2`) holds net classes whose track width and via limits `phoenix check` verifies. All of it is a prototype tried on schematics and boards made by hand and by the tests, never compared with the reference tool. The schematic editor (`docs/SCHEMATIC_EDIT.md`) is a prototype too, tried on schematics made by the tests only: reversible operations (place, move, turn, mirror, delete, copy and paste, values and references, wires, net labels, power ports and bus labels) in the module `edit` of the schematic crate, with the nets made again from the drawing; its state without a screen in the crate `eh3d-phoenix-schedit` (grid and snapping, selection, wires that follow the pins, a palette of symbols, the electrical check after each change, the transfer to the board with a preview and the net list for the simulator); the command `phoenix schedit`; and an editing mode of the window that has never been seen on a screen. A crate (`eh3d-phoenix-sim`) simulates circuits with a solver of our own (command `phoenix sim`, see `docs/SIM.md` and `docs/adr/0010-own-circuit-simulator.md`): a reader and a writer of SPICE-style netlists, the netlist of a schematic (made from a table of models and the attributes of the parts, with a report of what could not be simulated, `docs/NETLIST.md`), linear circuits, diodes (series resistance, junction capacitance, breakdown), bipolar and MOS transistors, voltage-controlled switches and op-amp macromodels by modified nodal analysis (`docs/SIM_NONLINEAR.md`), the DC operating point (Newton-Raphson with gmin stepping and source stepping as fallbacks and a report of its iterations and residual), the DC sweep of a source, AC sweeps with magnitude, phase and group delay, the noise at an output, transient analysis (backward Euler and trapezoidal, fixed step and an adaptive step that stops at the corners of the sources), CSV and JSON tables, and a check of its AC response against the ladder filters of the RF crate; it is a prototype tested with textbook values, closed-form solutions and properties, never compared with SPICE or with a measurement, and its device models are simple. A crate (`eh3d-phoenix-route`) holds the editing and routing logic that needs no window (commands `phoenix route` and `phoenix ratsnest`, see `docs/ROUTE.md`): the ratsnest of the connections still to be routed, a router for pieces at 0, 45 and 90 degrees that takes the width and the vias from the rules and the net class and stops in front of obstacles or goes around them, reversible editing operations with undo and redo, and the live check that reports what an edit adds and removes; a prototype tried on boards made by hand and by the tests, with no arcs, no copper zones and no push and shove. The same crate exchanges files with an external autorouter (command `phoenix autoroute`, see `docs/AUTOROUTE.md`): the board as a Specctra DSN file, a Specctra session read as a plan whose routes are checked against the rules and applied all or nothing, and an adapter that starts a program, off unless a settings file and a command line option both say so; a prototype tried with sessions made by hand, never with a real autorouter. A crate (`eh3d-phoenix-autoroute`) is an autorouter that needs no outside program (command `phoenix autoroute native`, see `docs/AUTOROUTE_NATIVE.md`): a grid from the rules, a search per layer with vias, rip-up and reroute within limits that count nodes, and a plan that is one reversible step and never adds a rule error; a prototype tried on small boards made by hand and by the tests, never on a real board. A crate (`eh3d-phoenix-zones`) fills copper zones (command `phoenix zones`, see `docs/ZONES.md`): the outline cut into convex pieces, the copper of other nets, the edge of the board and the zones of a higher priority taken out with exact integer polygon clipping by the clearance of the rules, thermal reliefs on the pads of the net, islands judged by area, width and connection, and a check that measures a fill against the board; a prototype tried on boards made by hand and by the tests, with the fill kept as convex polygons that is not yet written in the Gerber files. A crate (`eh3d-phoenix-lengths`) gives the copper length and the delay of each net, with the delay of each layer taken from the stack-up, judges groups of nets that must match in length and differential pairs by their length difference, width, separation and uncoupled length (command `phoenix lengths`, see `docs/LENGTHS.md`); a prototype tried on boards made by hand and by the tests, whose length is the total copper of a net and which tunes nothing. A crate (`eh3d-phoenix-script`) holds the script interpreter (commands `phoenix script run`, `phoenix script report` and `phoenix cam-import`, see `docs/SCRIPT.md`): a reader of script files of the command language of the previous workflow, a run of `GRID`, `LAYER`, `DISPLAY`, `CHANGE`, `WIRE`, `VIA`, `CIRCLE`, `RECT`, `TEXT`, `MOVE`, `ROTATE`, `DELETE`, `NAME`, `VALUE`, `SET`, `GROUP`, `RATSNEST`, `DRC`, `ERC`, `WRITE`, `OPEN` and `SCRIPT` as reversible operations of the board, all or nothing and with an undo that gives the original back byte for byte, a compatibility report that lists every command of every script as equivalent, adapted or pending with its cause (text, JSON and HTML) and a reader of output jobs into an export profile; it is a prototype built from the public description of the language and tested with scripts written for it, never compared with the original tool and never run on the author's own scripts. The same crate reads a second script language, `phoenix-script/2` (`docs/SCRIPT_API.md`, commands `phoenix script run`, `check`, `list` and `help`): variables, bounded loops and conditions on measures, queries over a board, a schematic or a library, and their editing operations made through the reversible operations of the model, a whole script being all or nothing and one step of the history, in a sandbox with limits of steps, memory and output and a data folder as its only file access; seven example scripts with their expected output are run by the tests; it is a prototype tried on documents made by hand only. A crate (`eh3d-phoenix-rfgen`) draws microstrip RF structures from the stack-up and the frequency (command `phoenix rfgen`, see `docs/RFGEN.md`): lines, mitered bends, curves and tapers, open and short-circuited stubs, the single-stub, quarter-wave and L matches built on the RF tools, stepped-impedance low-pass and coupled-line band-pass filters, a Wilkinson divider, a branch-line coupler, patch and dipole antennas and an edge SMA launch with a via fence; each result is one all-or-nothing batch of reversible operations of the board (the board crate gained operations to add and remove copper zones and footprints for it) with a report of the dimensions, the formulas used with their sources and ranges, the warnings and the rule check of the result, which is refused when it adds an error. It is a prototype tested with values of textbooks and with properties on boards made by the tests, and it has never been compared with an electromagnetic simulator or with a measurement; discontinuities and dispersion are not modelled, and the isolation resistor and the land pattern of the connector are generic. A crate (`eh3d-phoenix-libedit`) is the library editor (commands `phoenix libedit` and `phoenix footprint`, a library mode of the window, see `docs/LIBRARY_EDIT.md`): an EAGLE library in memory with reversible all-or-nothing operations on footprints, symbols and devices (pads, lines, arcs, texts, pins, openings of the mask and the paste, gates, variants and the connection of pins to pads) with undo and redo, checks with the codes `PHOENIX-LIB-001` to `014`, saving as a new file that is read back and compared with a copy of the original beside it, generators of footprints by the method of IPC-7351B whose values in `config/footprints.cfg` were entered by hand and are not checked against a datasheet, and the replacement of an item by the master candidate of the sanitizer only after the confirmation of each step; it is a prototype tried only on libraries made by its tests, no EAGLE has opened a file it wrote and its window has never been seen on a screen. A crate (`eh3d-phoenix-oracle`) holds reference cases for the calculations (command `phoenix oracle`, see `docs/ORACLE.md`): 121 cases in `tests/oracle/`, 96 of them cited with a published value or a closed-form solution, its source and its tolerance and run against the real functions of the stack-up, RF, simulator, rules, lengths and zone crates, and 25 pending with the reason and no number; passing them shows that a calculation reproduces a published formula or a closed-form solution, it does not compare anything with EAGLE, KiCad, a field solver, a SPICE program or a measurement (the plan to do so is written and has not been run), and it changes no state of this repository. An own corpus (`phoenix corpus`, `docs/CORPUS.md`) of 96 small pieces written by hand in the formats of the suite, with round trips between formats and properties on generated boards, runs the readers and the writers against answers worked out by hand; it holds no file of a maker and is not a comparison with EAGLE, KiCad or a CAM program.

## Capabilities

The official state of each capability is in REQUIREMENTS.md: 31 requirements: 21 `prototype` (PPCB-001, PPCB-002, PPCB-003, PPCB-007, PPCB-008, PPCB-009, PPCB-011, PPCB-012, PPCB-013, PPCB-014, PPCB-015, PPCB-016, PPCB-017, PPCB-019, PPCB-021, PPCB-022, PPCB-024, PPCB-028, PPCB-029, PPCB-030, PPCB-031) and 10 `planned`. This page never states a state that REQUIREMENTS.md does not.

## Open questions

* Which user-interface and rendering stack to use: candidates are egui on wgpu with a custom canvas, iced, Slint, or everything on wgpu. It is decided after a short prototype measured on small, medium and large boards. The prototype exists (egui on eframe with a canvas of our own, `docs/adr/0009-first-interface-stack.md`) and its choice stays provisional until the drawing is measured on a real screen; only the preparation of the data has been timed.
* Which 2D geometry library to use for offsets and boolean operations, decided with a benchmark on degenerate input.
* Whether the first golden files can be produced semi-automatically from the command line of the reference tool.
* Whether the simulator of our own (`docs/adr/0010-own-circuit-simulator.md`, provisional) stays the engine of the circuit simulation, and which existing engine to compare it with, once its licence and platform support are checked.

## Needs from other repositories

* EH3D-COMMON: the project container (`eh3d-container`), the diagnostic crate (`eh3d-diagnostic`) and the materials database (`eh3d-materials`, used by the stack-up calculation and by `phoenix materials`), already used; this repository builds next to it
* EH3D-CORE-LIBS: geometry, readers and the Gerber and Excellon writers
* EH3D-VALIDATION-LAB: the corpus and the golden-file oracle

## Known technical debt and omitted tests

* 3699 tests of the Rust code and 33 of the base; the inventory tests build their own folders and never touch a real project.
* The review of security (`docs/SECURITY_REVIEW.md`) was made by the project itself and no one else has read the code for it: it finds what a search of the source and the changes of a fixed generator find, it bounds the size of the input and not the memory, and it says what it does not cover.
* The tutorials (`docs/tutorials/`) are run by a test that compares the beginning of each output with the documented text, on small files written for them; several steps whose output was not worked out (the rule check of the schematic, the synchronisation, the fabrication package, the connectivity of the EAGLE pair, the Gerber check, the DXF of the panel, the comparison of footprints, the list of RF structures and three of the signal integrity analyses) are shown without being run, and none of the files has been opened in EAGLE, KiCad or a manufacturer's tool. The help in the eight languages is one paragraph for each topic and one line for each command: the lines of usage with every option stay in English.
* The advanced analyses of the simulator (`docs/SIM_ADVANCED.md`) have been tried on circuits written by the tests and on closed-form cases only: the poles and zeros come from a fit of the AC response that is refused when no model of up to `max_pole_order` poles fits, the crossings are interpolated between the points of the sweep, the Monte Carlo study has uncorrelated tolerances of resistors, capacitors and inductors only, and nothing has been compared with SPICE or with a measurement.
* The extended RF tools (`docs/RF_ADVANCED.md`) are estimates from ideal lumped elements and lossless quasi-static lines, tried with results worked by hand, textbook tables and networks made by the tests only: the bandwidth comes from a scan of the ABCD matrices with the values of the elements kept fixed, the effect of the standard values on a filter is the rounding of the values and nothing else, the simulated response of a filter is checked against the ABCD one and not against another program, and no response, mask or stability circle has been compared with a network analyser, a field solver or another RF program. The Legendre and the elliptic approximations are not implemented.
* The reference cases (`docs/ORACLE.md`) compare the calculations only with published formulas and closed-form solutions: the 28 pending cases and the whole plan of comparison with EAGLE, KiCad, a field solver and a SPICE program have not been run, and some tolerances are chosen in the case files and say so.
* The differential pairs (`docs/DIFFPAIRS.md`) have been drawn, tuned, corrected and checked on boards made by the tests only: no pair has been routed on a real board, the impedance is a quasi-static estimate that has not been compared with a field solver or a measurement, and the pair tool of the window has never been seen on a screen.
* The autorouter of our own (`docs/AUTOROUTE_NATIVE.md`) has been tried on small boards made by hand and on boards made by a generator with a fixed seed: no real board has been routed with it, nothing has been compared with another autorouter, its speed on a large board has not been measured, a differential pair is routed as two ordinary nets, and its button in the window has never been seen on a screen.
* Push and shove and the arcs of the board editor (`docs/SHOVE.md`) have been tried on boards made by the tests only: no real board has been routed with them, the planning of a push uses floating point and takes a pad as a disc, the design rules see an arc by its end points and the editor checks its chords itself, and the push tool of the window has never been seen on a screen.
* The copper zones of the board editor (`docs/BOARD_ZONES.md`) have been drawn, filled, cut, prioritised, copied and pasted on boards made by the tests only: the fill has never been compared with the fill of the reference tool, no real board has been poured into Gerber files and opened elsewhere, and the zone tool of the window has never been seen on a screen.
* The sheet symbols, repeated sheets and buses of the schematic (`docs/HIERARCHY.md`, `docs/BUSES.md`) have been tried on schematics made by the tests only: the expansion has not been compared with the hierarchy of KiCad or of EAGLE, the readers keep the structure of those files but not the parts inside an EAGLE module, no design from a real project has been read, and the tabs and the bus tools of the window have never been seen on a screen.
* The tests of the flow (`crates/eh3d-phoenix-cli/tests/flows_*.rs`) take a small EAGLE project and a small KiCad project, written by the tests, through the modules one after another (read, rule check, netlist, simulation, rules of the board, annotation back, panel, fabrication package, the package read again and compared with the project) and the editing of a board with undo and redo to the same bytes; each stage has an expectation worked out by hand and one assertion that names the stage. They prove that the modules agree on small hand-made projects, not that a project of a person goes through.
* `phoenix view --snapshot` writes the scene of the viewer as an SVG picture, so the drawing can be looked at without a window; it draws the layers in the colours of the window and not the highlights, the selection, the measures or the grid, and the picture has been looked at in no more than one browser.
* The window of the viewer has never been seen on a screen, a graphics card or an operating system: the lints of CI check that it builds, nothing more. The timing of `phoenix view --bench` covers the preparation of the primitives and the selection by position, not the drawing, and its numbers depend on the computer. The window of the imported Gerber files and the 3D window of the assembly are in the same case: their scenes, cameras and comparisons are tested without a screen and neither has been used with a mouse.
* The manufacturing export (`docs/EXPORT.md`) has been read back only by the parsers of EH3D-CORE-LIBS and by the import of this repository (`docs/GERBER_IMPORT.md`): no independent Gerber or Excellon viewer, no manufacturer and no assembler has opened a file of it, the rule for the rotation of a bottom part and the columns of the `jlc-like` profile are settings that nobody has compared with a real sample, and the thermal reliefs of a pour, back drilling and polygon pads are not written; the cutouts of the outline, rounded and not plated pads, the clear polarity of the cutouts and keep-away of a pour and the drill files of blind and buried vias are written and have been read back by the parsers of this repository only. The pick and place files, the solder paste stencil and the fabrication package (`docs/PNP.md`, `docs/STENCIL.md`, `docs/FABPACK.md`) are in the same case: no file has been loaded in a machine, made into a plate or sent to a manufacturer, the zip file has been read back only by the reader written for it, and the table of extra rotations of a machine comes empty.
* The Gerber X2 attributes of the export (`docs/GERBER_X2.md`) were written from the specification as the author knows it and not compared line by line with its text; no viewer, CAM program or manufacturer has opened a file with them, the structure check `phoenix gerber-check` is a subset chosen here, and the manufacturer and part number attributes are not written.
* The import of Gerber and Excellon files (`docs/GERBER_IMPORT.md`) and the panelization (`docs/PANEL.md`) have been tried on files and boards made by the tests only: the import has never read a file written by a CAD program or a manufacturer and its geometry has never been compared with a reference viewer, and no manufacturer has accepted a panel; the layers of a panel (copper, solder mask, paste, legend and drills of every copy, turned or mirrored, with the marks) are written by the export and read back by the import of this repository only, and the window that draws a panel has never been seen on a screen.
* The bill of materials with costs (`docs/BOM.md`) and the 3D assembly (`docs/ASSEMBLY3D.md`) have been tried on boards and files made by the tests only: the tariffs of `config/costs.cfg` are an example and not the quote of any maker, the prices are the ones of a file the user gives and are never checked, no STEP file from a component maker has been read, a component is only its enclosing box, no CAD program has opened the OBJ and STEP files it writes, and the 3D window that draws the scene has never been seen on a screen or used with a mouse. The local parts base (`docs/PARTS.md`) and the completion of the bill from it are in the same case: only bases written by the tests have been read, the prices are never checked, the footprints are checked against the IPC library of this repository, which is a prototype, and the assignment of a part to a symbol is a plan of the editor that no window offers yet.
* The deep reading of EAGLE files (`docs/EAGLE_DEEP.md`) has been tried on small files written for the tests only: the design rule file, the CAM job in its three forms, the part attributes, the variants and the layers are read as the formats are documented, no file saved by EAGLE has been compared with them, the loss report lists what the design model keeps from the readers as they stand, and a variant is applied to the bill of materials and the placement file but not to the schematic checks.
* The signal integrity estimates (`docs/SI.md`) are quasi-static estimates from closed formulas, tried on boards made by the tests only: the coupling of microstrips uses an inductive ratio from the images of two thin wires and a capacitive ratio estimated here, the loss is a single pole, the eye has neither reflections nor crosstalk, a crossed plane is found from the outline of the zone, and nothing has been compared with a field solver, a circuit simulator or a measurement; the pages of the books that the formulas come from are not verified.
* The common parts of the window (`docs/VIEWER.md`, `docs/SHORTCUTS.md`): the search, the measures, the layer presets, the list of the history, the themes, the keys that the settings change, the help and the remembered preferences are tested through the state that drives them and with boards and files made by the tests; they have never been seen on a screen or used with a mouse, the contrast of the themes is checked by a formula and not by eye, and the preferences have been written and read on the computer that runs the tests only.
* The DXF (`docs/DXF.md`) and the check against an enclosure (`docs/ENCLOSURE.md`) have been tried on drawings, boards and enclosures made by the tests only: no CAD program has opened a file they write or has written a file they read; ellipses, hatches, dimensions, texts and arrays of inserts of a drawing are listed and not read, the board keeps the cutouts of a drawing inside its outline as polygons of straight pieces, the components are boxes, the enclosure is a cavity with posts and not a model, and the STEP solid of the board holds the outline and its round holes only.
* The spatial index (`docs/SPATIAL.md`) and `phoenix perf` have been tried on boards and boxes made by the tests from fixed seeds only: the copper clearance check and the ratsnest give the same results with the index as without it on those boards and the counts of comparisons are linear on boards spread over a lattice, but no board of a real design has been used and no time has been measured; many objects close together give each query more candidates than a spread board does, and the fill of zones, the paste of a group, the export of the layers and the push of a track do not use the index.
* Printing (`docs/PRINT.md`) has been tried on boards, schematics and panels made by the tests only: the PDF has been read only by the checker of the crate and never opened in a real PDF reader or printed, the SVG only in one browser, the texts in Japanese and Chinese appear in a PDF as empty boxes, and the button of the window has never been seen on a screen.
* The model foundations are checked with generated and edge cases only: there is no design object on top of them yet, so the identities across save, migration and reopening are untested. Duplicate keys in an input JSON text are not detected before canonical writing. The system random source for ids is not cryptographic (ids need uniqueness, not secrecy).
* Not tested: a corpus of hundreds of thousands of files, folders synchronised by a cloud service, and links (they are skipped and counted; the test for it runs only on Unix-like systems).
* The kind of a file is read from its first bytes only: a file that starts like XML but is damaged later is counted by its start.
* `cargo deny` is not run in the CI yet: it needs a third-party action that the repository settings do not allow; `deny.toml` exists and has not been run on a computer.
