# EH3D-PHOENIX-PCB: requirements

This register is the single source of the state of each capability. Status values: planned, prototype, implemented, validated. Seventeen requirements (PPCB-001, PPCB-002, PPCB-003, PPCB-007, PPCB-008, PPCB-009, PPCB-011, PPCB-012, PPCB-014, PPCB-016, PPCB-017, PPCB-019, PPCB-021, PPCB-022, PPCB-024, PPCB-029 and PPCB-030) are `prototype` and the other 13 are `planned`: none is validated and nothing has been run on real design files. High test coverage is not proof of geometric or electrical correctness, so each requirement says how it will be checked and what result is expected.

| Requirement | Description | Status | How it will be checked | Expected result | Known limits |
|---|---|---|---|---|---|
| PPCB-001 | Design model with stable object identities and integer nanometre coordinates. | prototype | automatic: property tests over thousands of generated models | Identities survive save, migration and reopening; references never dangle. | Only the foundations exist: checked nanometre and micro-degree values with the 2^30 nm range, orientation predicates in 64-bit integers, arcs as end points plus a sweep, UUID v7 ids from an injectable generator, and canonical JSON. There are no design objects, no references, no project file and no operations yet, so identities across save and migration are untested. |
| PPCB-002 | Reversible operations with undo and redo across domains. | prototype | automatic | A failed operation leaves the model unchanged; undo restores the intended state. | Only the board model has operations (nets, components, pad nets, tracks, vias, copper zones, footprints) with an exact inverse, all-or-nothing batches and a replayable undo/redo history; tried on generated boards only. Schematic and other domains have none. |
| PPCB-003 | Own project format with one folder per domain, migrations, opaque data and atomic saving. | prototype | automatic: round trips, interruption tests | A corrupt file gives a diagnostic, never a panic; an interrupted save leaves a valid project. | The manifest, domains, links, migrations, opaque preservation, `must_understand`, read-only opening and atomic saving exist and are tested on generated projects; no migration is registered yet, the container's atomic replacement is tested but not inside a synchronised folder, and no real design has been saved. |
| PPCB-004 | Read and write EAGLE XML files (versions 6 to 9) with an import quality report. | planned | oracle: golden files, round trips | Nothing is lost silently; the report lists kept, transformed and dropped data. | Still `planned`: only a read-only summary exists (`eh3d-phoenix-eagle`: a bounded XML parser and counts of libraries, boards and schematics with consistency checks); it does not build the design model. The crate `eh3d-phoenix-eagle-board` writes a board of the model as an EAGLE XML file (layers, outline, packages, elements, signals, vias, polygons, silkscreen as strokes) and reads such a file into a board, compared by a signature without ids; the reader has only been tried on files written by that writer, no EAGLE has opened a written file, libraries are written from the footprints and symbols (`write_library`, read back by the summary reader only), schematics are written with their library, parts, sheets, nets and wires (`write_schematic`) and read back into the model (`read_schematic`, compared through a signature without ids), the reader having only been tried on files written by that writer, and what the format cannot say is reported (`PHOENIX-EAGLE-020`, `PHOENIX-EAGLE-021`). First measurement over copies of a private corpus of 2263 files (`.lbr`, `.brd`, `.sch`), checked by SHA-256 against their originals: 734 are read (324 per thousand: 527 boards, 199 schematics and 8 libraries, versions 6.0 to 9.6.2) and the XML tree of each comes back identical after being written and read again; 1057 start with the bytes 0x10 0x80 (`PHOENIX-EAGLE-012`) and 377 with 0x10 and another second byte (`PHOENIX-EAGLE-014`): the binary files of the old versions, which no reader here handles (counted by reading the first bytes of the files); 15 are files of other programs that use the same extensions (13 of KiCad, 2 of P-CAD; `PHOENIX-EAGLE-013`), 71 are XML but not EAGLE documents and 9 are of another kind (8 other binary files and one short text); the 734 read files raise one warning and no error. The rate is of the summary reader, not of the design model, and nothing is compared with the reference tool yet. |
| PPCB-005 | Read EAGLE binary files (versions 4 and 5), read-only, learned clean-room. | planned | oracle: pairs of binary and XML files | Same content as the XML written by the reference tool. | Not started: the contract for the pairs is written (`eh3d_phoenix_eagle::pairs`: one folder, each pair a binary file and its `.xml`, a manifest of SHA-256 hashes, the comparison of the two summaries, the codes `PHOENIX-EAGLE-015` to `PHOENIX-EAGLE-019`) and the pairs have to come from the owner of the files; no reader of the binary format exists. |
| PPCB-006 | Compare results with the reference tool through golden files. | planned | oracle with EH3D-VALIDATION-LAB | The rate of agreement per level does not drop; every failure is classified. | Not started: no limits known yet. |
| PPCB-007 | Extract connectivity of schematic and board. | prototype | oracle plus negative cases | Identical to the reference on the corpus; deliberately introduced errors are always found. | Prototype, not validated: the crate `eh3d-phoenix-rules` derives the nets from the geometry of pads, tracks, vias and zones with a joining tolerance read from the rule file (exact integer arithmetic; a pad that is not round only inside the limits of its inscribed and circumscribed circles; a zone joins only the copper of its own net inside its outline), reports copper of different nets that touches and nets that still have connections to route, and compares the nets of a schematic with those of a board by reference designator and pin number (missing nets, unconnected pins, board nets that join several schematic nets, names), with confirmed and inconclusive results in two lists; the schematic crate checks a schematic against a board (parts, designators, values, footprints, pins and nets as groups in both directions), the board crate computes the islands of each net and the schematic crate also holds a drawing (sheets, placed parts, pin positions and wires) whose wires are read as groups of pins and compared with the net list and with the board, without junction symbols, buses or net labels; arcs are judged by their end points, deliberate errors on hand-made boards are always found by the tests, and nothing has been compared with the reference tool, so it stays at prototype until it agrees with it on the corpus. |
| PPCB-008 | Design-rule checks in a fixed order: copper clearance, minimum width, drill and annular ring, board edge, mask, silkscreen over pads. | prototype | automatic plus oracle | Each finding carries a stable code; the report separates confirmed from inconclusive. | Prototype, not validated: the rule engine (`eh3d-phoenix-rules`) runs the checks in a fixed order against a rule file of its own (JSON, every length in nanometres, a missing field turns the rule off) or the `<designrules>` of an EAGLE board (the clearances are folded into the largest value and the parameters it does not use are listed): track width, via diameter, drill, annular ring, copper clearance of tracks and vias, distance to the board edge and drill spacing, each finding with its place, the measured value and the limit, plus the checks of pads, solder mask, zones and silkscreen of the board crate with their limit and no measured value; the report is text in eight languages or JSON, with confirmed and inconclusive findings in two lists, and `phoenix check` prints it. Arcs are judged by their end points (a proven finding or an inconclusive note), the shape of a pad only inside its inscribed and circumscribed circles, there is no rule per net class or per layer, deliberate errors on hand-made boards are always found by the tests, and nothing has been compared with the reference tool, so it stays at prototype until it agrees with it. |
| PPCB-009 | Export Gerber X2 and Excellon deterministically. | prototype | automatic: two independent viewers, byte comparison | Output matches the model; two exports at different times are identical. | Prototype, not validated: `eh3d-phoenix-export` writes one Gerber X2 file per layer (copper, solder mask, paste, legend and profile, each with `.GenerationSoftware`, `.FileFunction` and `.FilePolarity`; pads as circles, rectangles and obrounds, tracks with lines and arcs, vias, board outline, zones as their outline; the solder mask and paste openings grow or shrink by a value of the profile) and two Excellon files, plated and not plated, with the tools in the order of their diameters and slots (`G85`) for drilled oblong pads when the profile asks for them, through the writers of EH3D-CORE-LIBS, identical for the same board; a check reads the files back and compares the counts of pads, vias, holes, lines, arcs and regions and the bounding box of the outline with the model; the files are read by the parsers of this repository only, not by two independent viewers and not by a manufacturer, which is why it stays at prototype; no copper pour, no clearance, no blind or buried vias, no pad rotation other than right angles, no polygon pads (the board model has none), and the attributes of pads and nets are not written. The details are in `docs/EXPORT.md`. |
| PPCB-010 | Export and import assembly formats (pick-and-place board and job files, mounting data, BOM and placement CSV). | planned | automatic with real samples | A round trip keeps the placements within a stated tolerance. | Still `planned`: `eh3d-phoenix-export` writes a placement CSV (reference, value, package, X, Y, rotation, side, with the rule for the rotation of a part on the bottom side chosen in the profile: keep, mirror or half turn) and a bill of materials grouped by value and package, from the columns and headers of a profile, but no real sample of an assembler or of a machine has been compared, nothing is imported and the formats of pick-and-place machines are not written. |
| PPCB-011 | Export an `.eh3dproj` package at version 1.0.0 by default. | prototype | automatic: conformance vectors | A consumer of the package reads it; newer versions only when consumers declare them. | Prototype, not validated: `eh3d-phoenix-export` builds a 1.0.0 package with the layer files, the drill files, the placement file and the bill of materials through EH3D-COMMON, byte for byte the same for the same board; the identity and time stamp come from the caller or, in the reproducible form, from the content; the same files can be written to a folder with a manifest of SHA-256 sums; no consumer program has opened a package made by it yet. |
| PPCB-012 | Read KiCad schematics, boards and libraries. | prototype | oracle: public corpus with reviewed licences | The rate of identical connectivity does not drop. | `eh3d-phoenix-kicad` and the command `phoenix kicad-read` (`docs/KICAD.md`) read the files of KiCad 6 to 9 into the model of the EAGLE files: symbol libraries, footprints, schematics with their sheets (the nets are computed from wires, junctions, labels and power symbols, because the file stores none), boards in integer nanometres (layers and their order, nets, pads, tracks, arcs, vias, zones, the outline, silkscreen) and the project file, with an import quality report and a fidelity level in the format hub. They are written from the public description of the formats and tried on files written by hand for the tests (versions 6, 7 and 8, damaged files); they have not been compared with KiCad, there is no public corpus yet, and the connectivity rate is not measured, so the state stays at prototype. Left out and counted: graphics and texts other than silkscreen, buses, the setup of a board, the filled copper of zones, keep-out zones, 3D models; simplified: rounded, trapezoidal and custom pads, oval drills, units of one part, rotations that are not right angles. |
| PPCB-013 | Write KiCad schematics, boards and libraries. | planned | oracle | KiCad opens them and its checks agree. | Not started: no limits known yet. |
| PPCB-014 | PCB viewer: zoom, layers, highlighted nets, measures, grid and rule list. | prototype | automatic plus manual review | Frame time and latency are measured with small, medium and large boards. | Prototype, read only, not validated: the crate `eh3d-phoenix-viewer` (command `phoenix view`, `docs/VIEWER.md`) turns a board or a schematic (EAGLE files or the JSON of the model) into drawing primitives on coloured layers and tests, without a screen, the zoom and the pan, the visibility and the colour of each layer, the selection by position with a tolerance and a spatial index, the highlight of a net, the measure and the position of the pointer; `phoenix view --bench` times the preparation of the primitives and the selection on boards of 1 000, 20 000 and 200 000 primitives. A window of egui behind the `gui` feature draws it and has never been seen on a screen, so the frame time and the latency of a click are not measured. No grid, no rule list, no ratsnest, no view from the bottom and no drawing of the symbols of a schematic beyond the box around their pins. |
| PPCB-015 | PCB editor: select, move, rotate, copy, delete, place, properties. | planned | automatic: operations tests | Every edit is a reversible operation. | Still `planned`: there is no window and no selection of parts, copying or placing. The operations that move and turn a component, delete a track, move a vertex, change a width and add a via exist as reversible operations with undo and redo (`eh3d-phoenix-route`, `docs/ROUTE.md`), as part of the routing logic of PPCB-016. |
| PPCB-016 | Routing: 45 degree tracks and arcs, vias, widths per class, live rule checks, ratsnest and copper zones; a remote auto-routing task. | prototype | automatic plus oracle | A re-routed board opens in the reference tool without warnings and its rule check agrees. | Prototype of the logic that needs no window, not validated: `eh3d-phoenix-route` and the commands `phoenix route` and `phoenix ratsnest` (`docs/ROUTE.md`) make the ratsnest of a board, and route between two elements of a net with pieces at 0, 45 and 90 degrees, the width of the net class, vias sized by the rules, a mode that stops in front of an obstacle and a mode that goes around it on a coarse mesh with the fewest corners; a track it returns passes the rules, an impossible route is a code, and every edit is a reversible operation that reports the findings it adds and removes. It has been tried on boards made by hand and by the tests only. Arcs, copper zones, push and shove, a through via on a board of more than two layers and the remote auto-routing task are not written; the plans have not been opened in the reference tool and the speed on a large board has not been measured. |
| PPCB-017 | Schematic editor with electrical rule checks, transfer to the board and annotation by stable identity. | prototype | automatic | A simple project can be taken from start to finish inside the tool. | Prototype for the logic that needs no window, not validated: the electrical rule check (`eh3d-phoenix-erc`, `phoenix erc`), forward and backward annotation by the identity of the parts as a package that is tried as a dry run and can be undone (`eh3d-phoenix-sync`, `phoenix sync`) and net classes in the rule file (`docs/ERC.md`). Tried on schematics and boards made by hand and by the tests, never compared with the reference tool. There is no schematic editor, so a project cannot be taken from start to finish inside the tool. |
| PPCB-018 | Command console and script files, each command a reversible operation. | planned | automatic | The author's own scripts run with the same result as in the reference tool. | Still `planned`: there is no console. The script files, each command a reversible operation of the board, are the prototype of PPCB-019. |
| PPCB-019 | Script interpreter for the existing scripting language, sandboxed, with a compatibility report per script. | prototype | oracle plus negative tests of the sandbox | Each script is reported as equivalent, adapted or pending with the cause. | Prototype, not validated: `eh3d-phoenix-script` and the commands `phoenix script run` and `phoenix script report` (`docs/SCRIPT.md`) read script files, carry out `GRID`, `LAYER`, `DISPLAY`, `CHANGE`, `WIRE`, `VIA`, `CIRCLE`, `RECT`, `TEXT`, `MOVE`, `ROTATE`, `DELETE`, `NAME`, `VALUE`, `SET`, `GROUP`, `RATSNEST`, `DRC`, `ERC`, `WRITE`, `OPEN` and `SCRIPT` as reversible operations of the board (all or nothing, with an undo that gives the original back byte for byte) and list every command of every script as equivalent, adapted or pending with its cause, as text, JSON and HTML, without running it. File access needs a permission and an allowed folder, with relative paths only, and the limits are in `config/script.cfg`. It was built from the public description of the language only and tested with scripts written for it; it has not been compared with the original tool or run on the author's own scripts, selection by pointing, curved wires, mirrored placement, the creation of layers and the other commands of the language are pending, and the sandbox is checks inside the program and not a separate low-privilege process. |
| PPCB-020 | Run output jobs of the reference tool. | planned | oracle: golden files | Same Gerber files as the reference tool. | Still `planned`: only the reading half exists. `phoenix cam-import` (`docs/SCRIPT.md`) reads an output job into a profile of the export and reports what could be translated; no job is run and no file is compared with the reference tool. |
| PPCB-021 | Library sanitizer: inventory, geometric hash, fuzzy matching with manual confirmation, replace-and-relink with backup. | prototype | automatic plus oracle | Replace-and-relink changes neither layout nor rule results on what it processes. | Prototype, analysis only, not validated: `eh3d-phoenix-sanitizer` and the command `phoenix sanitize` (`docs/SANITIZER.md`) take the inventory of a folder of EAGLE libraries, hash every footprint and symbol canonically (independent of order, names and small roundings, with optional turns, mirror and shift), score near duplicates against a threshold, form groups for the owner to confirm, name the item to keep and write an HTML report, the same report as JSON and a plan that is never applied. Replace-and-relink with backup is not written; it has only been tried on libraries made by its own tests, never on real libraries, and its tolerances are defaults. |
| PPCB-022 | Circuit simulation through an existing engine with reference cases. | prototype | automatic: analytic solutions | Results agree with the analytic cases within a justified tolerance. | Prototype, not validated: the first solver is our own (`eh3d-phoenix-sim`, command `phoenix sim`, `docs/SIM.md`; the choice is provisional, `docs/adr/0010-own-circuit-simulator.md`). It solves linear circuits and circuits with diodes (series resistance, junction capacitance, breakdown), bipolar and MOS transistors and op-amp macromodels by modified nodal analysis (DC operating point with gmin and source stepping, AC with group delay, noise, transient with an adaptive step that stops at the corners of the sources) and the cases of the textbooks agree with the formulas: a divider, the RC time constant, the corner of the RC low-pass, a series RLC with its resonance and Q, a half-wave rectifier with and without a filter capacitor, a Zener regulator, a transformer from coupled inductors, a common-emitter amplifier, a current mirror, a CMOS inverter, a non-inverting op-amp amplifier, the thermal noise of a resistor and kT/C, and ladder filters of the RF tools. It has not been compared with an existing engine, which is what the requirement asks for, the device models are simple and a dense solver has a size limit. |
| PPCB-023 | Power-supply design assistant with declared ranges of validity. | planned | automatic plus physical measurement | Two real supplies are built and measured, and the deviation is understood. | Not started: no limits known yet. |
| PPCB-024 | RF tools by levels (analytic calculators first). | prototype | automatic plus measurement | Each level states its scope and limits. | Two analytic levels exist. The first is `eh3d-phoenix-stackup` and the command `phoenix stackup` give the impedance, effective permittivity, conductor and dielectric loss, delay and guided wavelength of microstrip, stripline (centred and offset), coplanar waveguide with and without a ground plane and edge-coupled pairs from published quasi-static formulas, and the track width for a target impedance, with the Dk and Df of a layer taken, when asked, from the materials database of EH3D-COMMON at the frequency of the calculation between the points a datasheet publishes (`phoenix stackup --material ID`, `phoenix materials`). Each formula is documented with its source and its range (`docs/STACKUP.md`) and a result outside the range carries a warning. It has not been compared with a field solver or with the measurement of a board; the offset stripline and the coupled pairs are approximations; dispersion, solder mask in the field, even and odd modes, discontinuities and vias are not modelled. The second is `eh3d-phoenix-rf` with the command `phoenix rf` (`docs/RF.md`): a reader and writer of Touchstone files, the S, Z, Y and ABCD parameters of two-ports with their conversions and figures (VSWR, losses, group delay, gain, stability, passivity), L networks, single stubs and quarter-wave sections for complex impedances, the coordinates of the Smith chart, and Butterworth, Chebyshev and Bessel ladder filters of ideal components. It is tested with values of textbooks and with properties and has not been compared with a network analyser, a field solver or another RF program; the filters have no loss, parasitics or tolerance of components, there are no noise or gain circles and no Touchstone version 2 keywords; nothing in either crate is an RF simulation. A third level draws structures: `eh3d-phoenix-rfgen` and the command `phoenix rfgen` (`docs/RFGEN.md`) calculate and draw on the board, from the stack-up and the frequency, microstrip lines, mitered bends, curves, tapers, stubs, the single-stub, quarter-wave and L matches, stepped-impedance low-pass and coupled-line band-pass filters, a Wilkinson divider, a branch-line coupler, a patch and a dipole antenna and an SMA launch with a via fence, as reversible operations of the board with a report of the formulas (each with its published source and range) and the rule check of the result. It is a prototype: the formulas are tested with values of textbooks (the miter, the open-end extension, the band-pass example and the stepped-impedance example of Pozar, a patch at 2.4 GHz on FR-4) and the structures with properties (the rules pass, undo gives the board back), the model of coupled microstrips is marked prototype, and nothing has been compared with an electromagnetic simulator or a measurement; discontinuities, dispersion and the isolation resistor and connector land patterns are not modelled. |
| PPCB-025 | Bounded assistance by artificial intelligence. | planned | automatic: policy tests | Its proposals are reviewable differences and it never creates or starts machine jobs. | Not started: no limits known yet. |
| PPCB-026 | Mechanical steps: 3D view, STEP/IDF/glTF export, fit check against an existing enclosure. | planned | automatic plus review | Exports re-read with the same dimensions. | Not started: no limits known yet. |
| PPCB-027 | Computing tasks on the EH3D server. | planned | automatic: equivalence tests between backends | Same task gives the same result in process, as an external process and on the server. | Not started: no limits known yet. |
| PPCB-028 | User-facing text in eight languages from one source with stable keys. | planned | automatic: key checks in CI | No missing or extra keys. | Not started: no limits known yet. |
| PPCB-029 | Stable diagnostic codes from a registry kept in this repository. | prototype | automatic: a test per code | A code is never reused or renumbered. | The model, project and board crates map every failure to a registered code and keep `docs/ERROR_CODES.md` in step by test; not every code is produced by a test of its own yet. |
| PPCB-030 | Redacted mode for runs over a private corpus. | prototype | automatic: leak test | Only codes, counts, levels and hashes leave the machine. | Only the inventory command has it: its report holds counts, kinds, declared versions and one fingerprint, with a leak test over file names, folder names and file contents. The other runs it is meant for do not exist yet; tried only on folders made by the tests. |

Rules: a claim of correctness names the corpus, the tolerance and the tool version it holds for. A phase is complete when the measured rate does not drop, every failure is classified and fixed or documented, and the measured figure is reported.
