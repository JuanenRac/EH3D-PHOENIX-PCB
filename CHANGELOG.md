- Add the crate `eh3d-phoenix-route`, the editing and routing logic of the board without an interface. The ratsnest is a minimum spanning tree per net over the islands that the connectivity of the board finds, with the closest points of two islands as the distance and every tie broken by the lowest index, so the same board always gives the same lines. The router joins two elements of a net (a pad, a via or the end of a track) with pieces at 0, 45 and 90 degrees, the width of the net class and vias whose drill and diameter follow the rules, the class and the annular ring: the mode that stops walks the straight way and ends, to the nanometre, in front of the first obstacle, and the mode that goes around searches a coarse mesh anchored at the start with a cost of length plus a penalty for every corner and every via, finishes with one or two straight pieces to the exact end and changes layer with a via when that is needed. Distances to the copper of other nets and to the edge of the board are compared exactly with integers, a pad is avoided as the smallest circle around it and an arc as a polyline, and a plan is judged on a copy of the board by the rules (and must join both elements in the connectivity) before it is returned, so an impossible route is an error with a code and never a broken track.

- Add the crate `eh3d-phoenix-sim`, a circuit simulator of our own for linear circuits and circuits with diodes, with no dependency beyond the complex numbers of the RF crate. The netlist in memory has a reader and a writer of SPICE-style text (`R C L V I`, the dependent sources `E G F H`, coupled inductors `K`, diodes with the Shockley equation, `.param` with expressions between braces, `.model`, simple `.subckt`, the unit suffixes `f p n u m k meg g t mil`, sources with `DC`, `AC`, `SIN`, `PULSE` and `PWL`) whose errors have a code and say the line, and what it writes reads back as the same netlist. The analyses are modified nodal analysis with a solver written for the crate (Gaussian elimination with partial pivoting, real and complex, that names the unknown a singular matrix leaves undetermined): the DC operating point with Newton-Raphson for diodes (voltage limiting, source stepping as a fallback, a report of nodes with no path to ground), AC sweeps (linear, per decade, per octave) with magnitude, phase and group delay, and transient analysis (backward Euler and trapezoidal, fixed step or a simple adaptive step, initial conditions). The netlist of a schematic is made from its nets, the values of its parts and the nets that mean ground, with a report of every part and pin it could not translate. A coherence check simulates a ladder filter of the RF crate and compares magnitude, phase and group delay with its ABCD response. Results are deterministic CSV and JSON tables that say they are an own numerical approximation. Every limit, tolerance and default is in `config/sim.cfg`; the codes are `PHOENIX-SIM-001` to `PHOENIX-SIM-021` with titles in the eight languages. It is a prototype tested with values of the textbooks (divider, RC time constant, low-pass corner, series RLC with its resonance and Q, half-wave rectifier, transformer from coupled inductors) and with properties (superposition, conservation of current, repeatable results); it has not been compared with SPICE or with a measurement.

- **The base that every repository of the suite has:** the manifest, the README files in eight languages, this changelog, the CI workflow, the issue and pull-request templates, and the shared checks of EH3D-DOCS (the repository check and the drawers of the two README pictures).
- **A planned project, described honestly:** the scope, the requirements (all planned), the relations with other repositories, the threat model, the decisions that apply and the rules for writing code are in `docs/`; there is no code yet.
- Add the crate `eh3d-phoenix-bom` and the command `phoenix bom`: the bill of materials of a board (and of the parts of a schematic that are not placed) grouped by value, footprint, maker and part number with the references of each line, prices by quantity break read from a local CSV or JSON file (nothing is fetched from a network), the cheapest supplier for the quantity of the batch with the waste, the cost per board and per batch, the parts without a price or a footprint listed, and an estimate of the cost of the boards from the area, the layers, the thickness and the holes with the example tariffs of `config/costs.cfg`.
- Add the writing of the bill as CSV, JSON and HTML that are the same every time, with the cells of the CSV quoted (and a cell that a spreadsheet would run as a formula made text) and the HTML escaped; the files are written only as new files and a file that exists is never replaced.
- Add the crate `eh3d-phoenix-assembly3d`, the module `scene3d` of the viewer and the command `phoenix assembly3d`: a model for each footprint from a local table (a STEP file or a box written in the table, with a shift and a turn), a reader of the least geometry of a STEP file (the box of a plain box, and for any other solid the box that encloses it with a finding, never an invented shape), the scene of the board with the thickness of its stack-up and its components as data, collisions between the boxes, a height limit, components that leave the outline, and a simplified OBJ and STEP export of the board and its components, written only as new files.
- Add the codes `PHOENIX-BOM-001` to `018` and `PHOENIX-3D-001` to `018` in the eight languages, the settings `config/costs.cfg` and `config/assembly3d.cfg`, and document the bill in `docs/BOM.md` and the assembly in `docs/ASSEMBLY3D.md`, with their state in `docs/REQUIREMENTS.md` and `docs/STATUS.md` and what is left out in `docs/NOT_YET.md`.
- Bring the test counters up to date: 1900 tests of the Rust code (counted from the sources) and 3 of the base.
