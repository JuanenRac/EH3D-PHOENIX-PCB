# Changelog

All notable changes to this project are documented here.

## [Unreleased]

- **Library files with long decimals are read as drawings:** a number with more than six decimals no longer turns its pad, line or text into XML that cannot be edited; it is read to the nearest millionth, so the item is drawn, checked and edited like any other. In a sample of a private collection this was the case of about one library in five that is not in the old binary form.
- **Those numbers are saved as they were:** the text of each is kept beside its item and written back for as long as the value is the one that was read; an edited value is written as the new one.
- **A number with an exponent is read, and the place of a gate is no longer lost:** an exponent is worked out without floating point, and a gate of a device set whose place had many decimals is no longer moved to the origin.

## [0.1.6] - Board editor operations, user programs that read most of a real folder, named values and files in one allowed folder, EAGLE reader measured on real boards

- **Most of the user programs of the owner's list can now be read:** `#usage` texts one after the other, `f(void)`, `enum`, `numeric` arrays, `int(x)`, `real(x)`, `char(x)` and `string(x)` as conversions, a walk or a layout over a single statement, a backslash before a character that is no escape (it stands for the character), a text that goes on in the next line and the end-of-file mark of old systems are no longer problems of reading. Measured on the folder of the owner (893 programs, aggregate figures only): programs with problems of reading went from 748 to 38.
- **More functions and values of the language run:** `sort` (several arrays by the first one, as numbers for numbers and `numeric` arrays), `lookup`, the character tests `isalnum`, `isalpha`, `isdigit`, `isspace`, `isupper`, `islower`, `ispunct`, `isxdigit`, `tolower`, `toupper`, `sheet(S)` over the sheets of the schematic, `dlgFileOpen`, `dlgFileSave` and `dlgDirectory` (cancelled without a window), `angle1` and `angle2` of an arc, and the constants `EXIT_SUCCESS`, `EXIT_FAILURE`, `EAGLE_VERSION`, `EAGLE_RELEASE` and `EAGLE_SIGNATURE`. The programs that the report counts as covered went from 21 to 207 and the ones the evaluator can run from 2 to 192.
- **The board editor can swap two pads:** the new operation `swap_pads` gives each of two pads the net of the other (the swap of two pins that do the same), refuses a swap that changes nothing or touches a locked part, and is one step to undo and redo.
- **A user program can write and read files in one folder that the settings allow:** `output(name, mode) { ... }` collects what the block prints and writes the file only when the block ends without an error, and `fileread`, `fileglob`, `filesize`, `filetime` and `fileerror` read there. The folder is `file_dir` in `config/ulp.cfg` or `--dir` of `phoenix ulp run`; with none set, no file is opened. A name outside it (absolute, with a drive, with `..`, a link) is refused, and the new limits `max_file_bytes` and `max_files` stop a run that goes beyond them.
- **A user program receives arguments and a clock:** `argc` and `argv[]` come from the arguments after `--` in `phoenix ulp run`, and `time()` is the clock of the machine or the one fixed with `--time SECONDS` (the same bytes every time); `t2string` with the usual codes of a format and `t2year`, `t2month`, `t2day`, `t2hour`, `t2minute`, `t2second` and `t2dayofweek` work in UTC.
- **The dialogs of a user program are a model in memory:** `dlgDialog` with its layouts and controls is recorded (title, kind, text and depth of each control) and answered as accepted without a window, `dlgMessageBox` answers its first button, and the action written after a control (`dlgPushButton("+OK") dlgAccept();`) is read and not run. The report now counts the `dlg` names as run by the evaluator.
- **More members of the design can be read by a user program:** `contacts` and `smds` of an element and a package (`C.pad` is the pad itself), `holes` (the unplated pads, placed or not), `texts` of the silkscreen, `instances` of the schematic, a sheet and a part, `library(L)` over the packages of the board, and `xc`, `yc` and `radius` of a piece of track that is an arc.
- **The security review names the files of a user program:** the code of the evaluator that writes the files of `output(name, mode)` is listed, with the ways it keeps (only inside the folder of `file_dir`, a name that is checked, a size limit, written when the block ends without an error), among the writes that do not create a new file, and the test that compares the source with the document knows it.
- **The board editor can change the width of a track:** the new operation `set_track_width` changes the copper width of a track as one step to undo, and refuses a width that is the same or not above zero.
- **The board editor can move a via and change its size:** `move_via` puts a via at another place and `resize_via` changes its drill and its pad (the pad stays larger than the drill); the tracks that end at the via stay where they are, so the rule check shows what no longer meets.
- **The board editor can cut a track in two:** `split_track` cuts a track after one of its pieces and `split_track_at` cuts it at a point of a straight piece, dividing the piece there; the first part keeps the id and the second is new, both are one step to undo, and a point that is not on a straight piece is refused.
- **The board editor can join two tracks:** `join_tracks` makes one track of two of the same net, layer and width whose ends meet, turning the second round when that is what makes them meet, and refuses tracks that differ or do not meet.
- **The board editor can tidy the tracks:** `tidy_tracks` takes out the pieces of no length and joins the straight pieces that follow each other in the same direction, in a net or in every net; a test with a fixed seed tries 200 random tracks and checks that the ends stay, that no piece has no length and that tidying twice changes nothing.
- **The board editor can change the value and the designator of a component:** `set_value` and `set_refdes` are one step each; a designator that is empty or that another component has, and a locked component, are refused.
- **The board editor can rename a net and merge two nets:** `rename_net` refuses a name that is empty or in use, and `merge_nets` moves the pads, the tracks and the vias of one net to another and removes it as one step, refusing while a zone is on it.
- **The board editor can put components on the grid:** `snap_to_grid` moves each component to the nearest point of a grid, leaves the ones that are on it, and refuses a locked component or a grid that is not above zero.
- **The Edit menu has the actions of the board editor:** *Tidy tracks*, *Join tracks*, *Snap to grid*, *Wider tracks*, *Narrower tracks* and *Swap pads*, in the eight languages, each enabled only while a board is being edited and the selection allows it (two tracks for the join, components for the snap, tracks for the widths); the same actions are buttons of the panel of the tools, and the width step is the new `width_step_nm` of `config/boardedit.cfg`.
- **The swap of pads is a tool of the window:** *Swap pads* takes a pad with the first click and swaps its net with the pad of the second click as one step to undo; the hint at the bottom of the drawing says which click is next, a swap that the board refuses drops the first pad and says why, and Escape drops it too.
- **The board editor shows what the rule check said after each edit:** a line under the tools gives the rule errors before and after, how many findings the edit added and how many it fixed, in the colour of the outcome (worse, better or the same), and the place of the first new error is kept so that the window can look at it; the report was made after every operation and was not shown.
- **A route can go on up to the last place that breaks no rule:** `BoardEdit::advance_route` takes a net, a layer, a start and a target, goes along the route on a copy of the editor and returns the corners that are reached and the last clear point of the leg that is blocked, to the nearest nanometre (the search is halved `advance_iterations` times, 30 by default), without changing the board; a test checks the stop at 10.45 mm in front of a track, a route that is clear to the end, one that is blocked at its start and that two runs give the same answer.
- **The reader of EAGLE files names the schematic files of another program:** the `.sch` files of an XML drawing with attributes and a net list (Xilinx ISE) are now `PHOENIX-EAGLE-013` (a file of another program) and no longer `PHOENIX-EAGLE-002` (not an EAGLE document).
- **The reader of EAGLE files was measured on a larger sample:** on the 21 boards and 40 schematics of the examples of the reference tool, and on a tenth of the libraries, half of the projects and half of the cached libraries of the owner (1772 files, aggregate figures only), all the XML files of EAGLE are read (890 of 890, the XML tree written back identical in every one); the files that are not read are the binary ones of the old versions (850, the largest cause: a reader of that format does not exist), files of other programs with the same extension (27) and a few that are not design files (5).
- **A user program can use the named values of the language:** the shapes of pads (`PAD_SHAPE_SQUARE`, `ROUND`, `OCTAGON`, `LONG`, `OFFSET`), the units and the styles of the grid (`GRID_UNIT_*`, `GRID_STYLE_*`), the directions and the lengths of pins, the shapes of vias, the fonts, the styles of wires, the ends of wires, the pours of polygons, the flags of pins and the numbers of the standard layers (`LAYER_TOP` to `LAYER_GUIDE`), from one table with a test that keeps the names apart.
- **The shape of a pad is a number, as the language has it:** `P.shape` answers `PAD_SHAPE_ROUND` for a circle, `PAD_SHAPE_SQUARE` for a rectangle and `PAD_SHAPE_LONG` for an oblong pad, so a program can compare it with the named value; it was a text before.
- **A wire has its run and its arc:** `W.dx` and `W.dy` are the run from the start to the end of a piece of track and `W.arc` is the piece seen as an arc, with its `xc`, `yc`, `radius`, `angle1` and `angle2`.
- **A user program can read the grid:** `B.grid` and `S.grid` give `unit`, `distance`, `altunit`, `altdistance`, `style`, `dots` and `multiple`; the model keeps no grid, so the answer comes from the new keys `grid_unit` and `grid_distance_nm` of `config/ulp.cfg` (a millimetre by default).
- **A user program can read the device, the gate, the symbol and the pins of a part:** `P.device` (its `name` and its `package`), `device.gates(G)` (`name`, `symbol`, `x`, `y`), `symbol.pins(N)` (`name`, `x`, `y`, `direction`) and `N.contact`, the pad of the package of the part with the number of the pin, on the element with the same reference; the model keeps one device for each part and says so.
- **A user program can read the segments of a net and the contacts of a signal:** `N.segments(G)` and `G.pinrefs(R)` (`R.part`, `R.pin`, `R.instance`) over the pins of a net of the schematic, and `S.contactrefs(C)` (`C.element`, `C.contact`) over the pads of a signal of the board; a pad of a placed element also answers `element`.
- **A user program can read circles and rectangles of the silkscreen:** `B.circles(C)` (`x`, `y`, `radius`, `width`, `layer`) and `B.rectangles(R)` (`x1`, `y1`, `x2`, `y2`, `width`, `angle`, `layer`), found by their shape because the board model has no such objects: two half turns that close are a circle and four straight pieces along the axes that close are a rectangle.
- **More functions of the language run:** `trunc` and the character tests `isgraph`, `isprint` and `iscntrl`.
- **The list of names of the compatibility report follows the programs of a real folder:** the read-only members of the objects of the design (`arc`, `device`, `symbol`, `contact`, `gate`, `dx`, `dy`, `grid`, `unit`, `visible`, `contours`, `pour` and others), the constants of the language by family and some functions are decided as allowed, so the programs that use them are no longer left as partly covered for want of a line in the list; the evaluator still says apart which of them it runs. Measured on the folder of the owner (892 programs, aggregate figures only): the programs counted as covered went from 207 to 674 and the ones the evaluator can run from 192 to 305.
- **Tests for all of it:** 48 new tests, among them the operations on a fixed board, the tidy of 200 random tracks with a fixed seed, the actions and the swap tool, the advance of a route, the line of the rule check, the eight languages of the new texts, the written and read form of every new operation, the named values and the new members and walks of the user programs on a small board and schematic built by the test; the tests that link the whole command line were left to the checks of the repository.

## [0.1.5] - A verdict and a common diagnostic for the Gerber check, a window on the docking frame with the library, the Gerber files, the 3D view and the boards as panels, a writer profile in every output and a reader and a read-only evaluator of the user programs of the reference tool

- **The library, the imported Gerber files, the 3D view and the panel of boards are panels of the docking frame:** they no longer cover the whole window while they are open. They are four new panels (`library_editor`, `gerber`, `view3d` and `boards`) that are hidden in every workspace until the person opens what they show; then they join the group of the board, which stays on the screen beside them, and each one can be moved, tabbed, floated, folded or closed like any other panel and brought back from the View menu. Opening a library no longer closes the board, and opening a board no longer closes the library. The entries of the menus that belong to the document stay on while a mode is open, the help shows the topic of the panel that has the focus, and a panel with nothing open says so in the eight languages.
- **An arrangement of the panels saved by the release before loads whole:** its panels stay where they were, in the workspace the person was in, and the four new panels are hidden; the first save writes them. The other way round works too: an arrangement written with the modes open loads in a window that does not know them.
- **`phoenix --shot` takes a picture of a workspace of the panels:** the new option `--workspace edit|review|compact` (also in `phoenix view --shot`) shows the board in that arrangement, and a picture still reads and writes no preferences, whichever workspace it asks for. `tools/make_shots.py` takes the board in the Review and the Compact workspaces besides the factory one.
- **A workflow takes the pictures of the window on a virtual screen:** `window-pictures`, run by hand, builds the window, takes every picture of `tools/make_shots.py` (the windows and the board in each workspace) and keeps them as an artifact of the run, so the pictures of the README can be renewed without building the window on a personal machine. It has not been run yet.
- **`phoenix ulp check` reads the user programs of the reference tool without running them:** the new crate `eh3d-phoenix-ulp` has a lexer and a parser of the shape of a program (directives, declarations, functions, the statements of C, expressions, and the calls that are followed by a block, which are the walks over the objects of the design, the output files and the dialogs). A mistake is a problem with its line and column and the codes `PHOENIX-ULP-008` to `PHOENIX-ULP-017`, the reading goes on from the next `;` or `}`, and the size, the tokens, the nesting, the chains of operators and the statements are bounded by the new `config/ulp.cfg`; a program nested a hundred thousand levels deep is refused, not overflowed. Text made by a generator with a fixed seed (random pieces, a good program with characters changed, the same program cut at every point, bytes that are not text) never stops it.
- **`phoenix ulp report` says what a user program uses and whether the list of names covers it:** for each program, the directives, kinds of statement, types, functions, members of objects and named values it uses with their counts and first places, the SHA-256 of the program, the problems of the reading, a note for each name that is allowed with limits, pending, refused by the sandbox or not on the list (`PHOENIX-ULP-019` to `PHOENIX-ULP-022`), and a verdict of covered, partly covered or not covered, as text in eight languages or as JSON that is the same every time. Nothing is run and the report says so: the evaluator and the sandbox of the decision record are not written, and the verdict says what the list would let through.
- **The names that the report knows are a data file:** `config/ulp_support.cfg` holds one `kind name status` for each line (`allowed`, `limited`, `pending` or `denied`, with `*` for a family of names such as `dlg*`), an exact name wins over one with a star, and `--support FILE` reads another list, so the scope follows the programs that are really used and not a manual. The list that ships is a first list.
- **The window is laid out with the docking frame of the suite:** `eh3d-dock` draws ten panels (the board, the layers, the properties, the components, the nets, the problems of the rules, the library, the console, the report and the tasks) that can be taken away, put back, moved, put in tabs, floated, folded into an edge, maximised and locked, in three workspaces by task (Edit, Review and Compact; there are no levels of experience) under a menu bar with File, Edit, View, Tools, Window and Help. An entry that cannot be chosen now is off and fires no key, and the keys of the program stay the master. The library, the imported Gerber files, the 3D window and the panel of boards still take the place of the panels while they are open, and the window has not been seen on a screen.
- **The arrangement of the panels is kept in the file of preferences:** the lines `dock.*` of the frame are written when the arrangement changed and never when it did not, read back at the start and checked line by line (a line of another shape is an error with its number), and a damaged arrangement gives the factory one and never stops the window; a picture reads and writes none.
- **Three new panels: the console, the components and the report:** the console keeps what the window said (notes, errors of a file and of the preferences) in order and without repeats; the list of components is in the order a person reads them (`R2` before `R10`) with a filter by words, a click that selects the item and puts it in the middle of the window, and the counts of the objects of each kind; the report gives the counts, the problems by severity and the connections still to be routed with no name, place or file in it, and a button copies it. The panels, the menus and every new message are in the eight languages (European Portuguese included).
- **The canvas is drawn behind one interface for the engine, and the report panel keeps the frame times:** `canvas_engine` in `config/viewer.cfg` chooses the painter of egui (the callback of wgpu of the decision record is not built, so asking for it keeps the painter and the console says so), and `frame_log_frames` frames are kept to show the median and the 95th and 99th percentile, the numbers of the first measurement of the record, with its verdict in code.
- **Five new settings in `config/viewer.cfg`:** `dock_check_every_frames`, `console_max_lines`, `component_rows_max`, `canvas_engine` and `frame_log_frames`.
- **The continuous integration reads the common library at its release 0.2.7, which holds the docking frame, and the lock file follows the readers of the shared libraries.**
- **Every Gerber, Excellon, IPC-2581 and pick and place file names the writer profile that made it:** one comment with one rule (`eh3d_phoenix_model::writer_profile`) holds the tag of the format and the name of the profile (`phoenix-export/1:generic`) and is written as the first line of a Gerber file at every level of X2, after the `M48` line of an Excellon file, after the XML declaration of an IPC-2581 file and as the field `writer_profile` of the JSON of pick and place; the settings of the stencil and of IPC-2581 gain a `profile` key; a profile whose name could not be written is refused before any file is made. The CSV files do not carry it (a loader reads them line by line) and the manifest of a package names the profile for them. The tests build every file twice and compare the bytes, and files that differ only by the name of the profile are the same once that line is taken out.
- **The decisions that were applied in the code are now written down as accepted, each with what implements it:** `docs/DECISIONS.md` records the library format, the identity of artifacts, determinism, versions and critical domains, licence identifiers, the common diagnostic crate, the two registries of codes, canonical JSON, the export version of the package, the router, the interface stack and the circuit engine, and marks what is accepted but not yet implemented. New records `docs/adr/0003-integer-nanometre-coordinates.md`, `0004-uuid-version-7-object-identities.md`, `0005-canonical-json-and-quantised-values.md` and `0007-geometry-library-and-degenerate-cases.md` explain the integer coordinates, the identities, the canonical JSON and the geometry library.
- **The interface stack is decided and the circuit engine record is closed:** `docs/adr/0009-first-interface-stack.md` now chooses egui with wgpu inside the window frame of the suite, keeping the measurements as the acceptance checks of the window, and `docs/adr/0010-own-circuit-simulator.md` keeps the own solver and compares it in the CI with an external engine started as a program, never linked.
- **A design record for an interpreter of the user programs of the reference tool, limited to a list of programs:** `docs/adr/0011-ulp-interpreter-for-the-owner-list.md` sets the order (a compatibility report first, then the reader, the evaluator and a sandbox in a separate process) and promises nothing about the whole language; no interpreter is written.
- **The register of requirements has the evidence and the test of each row, and a test checks it:** `docs/REQUIREMENTS.md` gains the columns Evidence and Test, seven requirements that had code move from planned to prototype (reading and writing of EAGLE boards, the oracle frame, the assembly files, script files, the reading of output jobs, the first mechanical steps and the server mode), and `crates/eh3d-phoenix-model/tests/requirements.rs` checks that every row that is not planned names a test that exists and that nothing is validated on the evidence of the own tests alone.
- **The geometric check of Gerber files tells what is confirmed from what is inconclusive, and its findings become the common diagnostic:** a report has a verdict (`failed`, `inconclusive` when a check was skipped, a layer was missing or the profile is not verified, or `confirmed`), the JSON carries the verdict and the two counts, and `finding_diagnostic` turns each finding into the diagnostic of the suite with its code, layer and numbers, marking a check that could not be made as inconclusive.
- **The library of typical stack-ups can name the record of the materials database for each of its materials:** `config/stackup_library.json` has an optional database id and, when there is none, a note that says why (both materials are figures of a maker's calculator, not laminates), a file with neither is refused, and a test checks that every id the file names is in the database.
- **A map of the work to the phases of the roadmap:** `docs/PLAN_MAP.md` lists what each phase has in the repository, the requirements it serves and the differences from the roadmap that are still open.
- **The CSV of the check of Gerber files is created exclusively:** the file is opened as new and the check refuses a name that exists, in one step, so a file of the person is never replaced and no race can slip between the test and the write.
- **A bounded reader of the archive of an ODB++ job (`.tgz`, `.tar.gz` or a plain tar), for the basic subset:** `read_odb_archive` lists the entries, finds the steps under `steps/` and reads `matrix/matrix` with the reader of the matrix, in memory and writing nothing. The archive is hostile until shown otherwise: limits on its size, the entries, one entry, all of them once unpacked, how much the unpacking may grow (a bomb is stopped by the ratio before it is unpacked), the depth of a path and the length of a name; the CRC-32 and the size of the gzip trailer and the checksum of every tar header are checked; and an empty, absolute, drive-letter, backslash, `.` or `..` path, a path twice in any case, a link of any kind, a device, an extension header, a size that is not plain octal and a cut archive are refused by name. Seven tests build synthetic archives (stored and fixed-code deflate, tar headers by hand) and damage them at random without a panic.
- **`phoenix assembly3d --glb FILE` writes the board and its components as a binary glTF 2.0 file with a profile of our own (`phoenix-board-glb/1`):** one node, mesh and triangle primitive for each prism with its name as the stable identifier, positions in metres with the axes of glTF, flat normals, the bounds of the accessors, one material for each role with the colours of `config/glb_profile.cfg`, metadata in the asset, and the same bytes for the same scene. A concave outline is cut by ear clipping and a prism that crosses itself, has no height or has a name used twice is refused with its name. Seven conformance tests read the file back (container, chunks, accessors, bounds, indices, normals, axes, determinism); the drilled holes and the layers of the stack-up are not in the file yet (`docs/ASSEMBLY3D.md`).
- **`phoenix check --gerber-dfm FOLDER|ZIP --profile NAME` checks the geometry of Gerber and Excellon files against a maker:** the spacing between separate pieces of copper, the width of tracks and arcs, the annular ring of plated holes in the worst case (the drill off by a registration error from the settings), copper at the edge of the outline, the bridge of solder mask between openings, legend over exposed pads, a via inside an open pad and floating copper, each with the figures of the profile (the profiles that come with the program are not verified, and the report says so). The shapes are made with the 2D geometry of the shared libraries. The report is text, JSON or CSV in the eight languages with the stable codes `PHOENIX-GDF-001` to `-011`, the exit code is 2 when the verification is not passed, 0 when it passes and 1 when the command could not run, and a ZIP archive is read in memory with limits. The method settings are in `config/gerber_dfm.cfg`; `docs/GERBER_DFM.md` says what the check does not know (nets, positive masks, clear polarity).
- **An adapter from the shared Gerber reader to the model of the importer, with a comparison of both readings:** the new module `core_adapter` of the Gerber crate reads a file with the reader of the shared geometry and format libraries and gives the layer in the model of this crate (flashes, lines, arcs, regions with their arcs cut, apertures, attributes of the file, units converted to nanometres), names what it cannot give yet (macro apertures, turned flashes, pens that are not round, blocks, object attributes, negative images) and marks the layer incomplete; `compare_layers` shows where it and the old reader differ. The old reader is not replaced, and `docs/GERBER_IMPORT.md` says what is left before it can be.
- **The quick library of laminates reads the materials database of the suite instead of keeping figures of its own:** the 17 entries of the stack-up crate are now records of `eh3d-materials`, linked by `config/laminate_links.json` (format `phoenix-laminate-links/1`, which also says at which frequency the constant and the loss are read), so there is one source of the figures. The module needs the feature `materials` (on in the command line), a figure the record lacks is undefined, a bad links file or a link to a record that does not exist is refused with what is wrong, and the figures that the database should gain are listed in `docs/MATERIALS_GAPS.md`.
- **The export builds against the newer readers and writers of the shared geometry and format libraries:** the Gerber and the Excellon files that are written now fill the fields that the readers gained (dialect, image parameters, attributes of X2, declared plating and notes of the tools) with their neutral values, so the files are byte for byte the same as before.
- **`phoenix ulp run` runs the part of a user program that only computes and reads:** the evaluator of `eh3d-phoenix-ulp` runs whole numbers of 64 bits and real numbers that are never infinite or not-a-number, texts, arrays that grow, the functions the program defines (with recursion), `if`, `for`, `while`, `do` and `switch`, the pure built-in functions (mathematics, the conversion of units, texts and the parts of a file name), `printf`, and the read-only walks over a board and a schematic (`board(B)`, `B.elements(E)`, `E.pads(P)`, signals, wires, vias, polygons, layers, packages, parts, nets and sheets, with their members, given with `--board` and `--schematic`). It opens no file, starts no program, asks nothing of the clock or the environment and cannot change the model: a file, a command, the clock or an assignment to a member of an object is an error with a code, and a name that the list of names allows but the evaluator does not write yet is an error and never a made-up value. The same program and design give the same bytes. It runs in the process of the caller; the sandbox in a process of its own is still not written.
- **A run is bounded, and the exit code says what happened:** five new lines of `config/ulp.cfg` (`max_steps`, `max_memory_bytes`, `max_eval_depth`, `max_output_bytes` and `max_array_elements`, each with its range) stop an endless loop, a text that doubles, a function that calls itself without end, a program that prints for ever and an array that grows without end, and nothing is printed when a run ends in an error. `phoenix ulp run` exits with 0 when the program ran (and, with `--expect FILE`, its output is the expected one), 2 when the verification did not pass (other output, or `exit` with a number other than zero) and 1 when it could not be run.
- **The compatibility report says whether the evaluator runs a program:** the JSON has `evaluator`, `sandbox`, `runnable`, `not_run` and `runs` in each use, and the text says in the eight languages which names the evaluator does not run, apart from what the list of names says, because a name can be allowed by the list and not be written yet.
- **Seventeen new codes, `PHOENIX-ULP-025` to `PHOENIX-ULP-041`:** the limits of a run, a type that the operation does not accept, a division by zero, a number out of range, a name that is not defined, an index out of range, something the sandbox does not allow, something the evaluator does not run yet, a design that was not given, wrong arguments, a change to the design, a program with problems of reading, a format that does not match its arguments and a verification that did not pass, with their titles in the eight languages.
